# /optimize — 설치 문서 부피·밀도 최적화 (이 repo 전용)

**역할 구분(유지보수 4축)**: `/reverify`=외부 최신성 · `/audit`=내부 정합성 · 실적용 검증=경험 결함 · **`/optimize`=비대 제거**. 감사·재검증은 구조적으로 "추가" 쪽으로 편향되므로(5회차 실측: 처방 대다수가 추가 → 문단 2,070자·버전 표가 문서의 30%), 반대 방향 힘은 이 절차가 담당한다. **새 기능·새 규칙을 넣지 않는다 — 말 그대로 최적화만.**
**권장 시점**: 감사·실적용 반영이 몇 차례 쌓인 뒤(문서 합계가 눈에 띄게 성장했을 때), 또는 릴리즈 정비 전.

## 0. 측정 (베이스라인)
문서별 총 자수·줄 수·버전 표 비중(표가 끝나는 `※ 갱신 시` 줄까지)·600자+ 문단 수·경위 표기(발견 ID `[GHSFMLR]\d+`·`실사례|실측|실적용 발견|docs/audit-`) 개수를 재서 목표를 정한다. 수치가 없으면 "줄었다"를 증명할 수 없다.

## 1. 압축 (규칙 불변)
- **버전 표 행 = "무엇이 바뀌었나" 요지만.** 행 수·버전 번호·날짜는 보존(check.ps1의 시간순·결번 검사 전제 + 재적용 버전 diff의 데이터) — **예외는 R20 버전 표 병합**(25행 초과 시 가장 오래된 행부터 축 요약 한 줄로 버전 행 15개 이하까지(병합 행 제외). 이 스킬이 집행자다). 감사 파일 참조·발견 ID·과거 상태 서술 제거. **"정정"을 "확정"으로 바꾸는 식의 주체·방향 변경 금지** — 서사가 깨진다.
- **본문 = 규칙 + 한 줄 귀결("~하면 ~가 깨진다")까지.** 경위 괄호(날짜·실측·발견 경위)만 제거하고 조건·귀결은 남긴다.
- **불변 영역**: 01 §F-1 정본 블록·§F-2 템플릿(설치 페이로드 — 기설치본과 어긋남 churn), `docs/RULES.md` **마커 문자열**(식별자 — 실측: 마커 한 개 소실로 check.ps1 FAIL).
- **삭제는 추가만큼 위험하다** — 첫 실행의 회귀 4건이 전부 삭제에서 나왔다(마커 소실·서사 왜곡·주체 변경·조건 소실). 겉보기 "경위 문장"이 규칙 대장의 배선점일 수 있다.

## 2. 검증 루프 (압축 → 아래 셋 → 발견 수정 → 반복)
1. **기계 검사**: `pwsh -File scripts/check.ps1` — 버전 4축·시간순·표 파손·마커 전부 통과.
2. **적대적 diff 검토**(에이전트): `git diff`에서 ① 의미 왜곡(다른 주장·바뀐 주체·반대 방향) ② 규범 손실(규칙·조건·귀결이 지워짐) ③ 소비자 단절(지운 문구를 타 문서·스킬이 인용) ④만 보고 — 정보량 감소 자체는 보고 대상이 아니다(그게 목적).
3. **실적용 테스트**: 신규 설치 완주(scratchpad 빈 repo — 절차 공백 탐지) 또는 playground 재적용 시뮬레이션(읽기 전용 — 압축된 표만으로 재적용 요약이 성립하는지).

## 3. 마무리
- 문서별 버전 bump 한 줄(`**최적화**: … 압축(규칙 불변)` — 이 행 자체도 요지만) + CLAUDE.md 표 동기화.
- 테스트가 찾은 절차 공백 중 **한 줄 처방이 서는 것만** 함께 반영하고, 판단이 필요한 것은 PROJECT_PLAN 관찰로 등재(1회 재발 후 배선).
- **PROJECT_PLAN — 이번 회차를 촉발한 `다음 /optimize` 줄을 먼저 닫고, 다음 주기를 `다음 ○○: YYYY-MM경` 형식으로 갱신**한다(이 형식이라야 `/resume` 예정일 안내가 발화한다 — 촉발 줄을 안 닫으면 그 안내가 상시 오보가 된다).
- PROGRESS 최상단 append(**아카이브 포인터가 있으면 그 줄 아래부터** — 포인터는 최상단 고정)(절감 수치 = 전/후 측정값), 방침 변경이면 DEC, check.ps1 통과 후 커밋·푸시(이 repo 상시 허용).
