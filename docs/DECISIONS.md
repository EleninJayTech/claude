PROJECT_PLAN에 관찰로 올라 있던 덕에 교차 확인으로 잡혔다. `/audit` §2의 재검증은 발견뿐 아니라 **부정 판정에도** 걸어야 한다. **⑤ 잠복 결함은 그 자리에 새 내용이 들어올 때 깨어난다** — `04`의 빈 인용 줄은 표 **끝**에 있어 뒤따르는 행이 없던 탓에 08-20 수리 목록에서 빠졌고, 이번 bump 행이 그 뒤로 들어가자 발화했다. - **DEC-20260821-bsjeong87-04** — **설계해 둔 처방도 집행 시점에 다시 고른다 + 사례 0건이면 처방하지 않는다**(wave형 시나리오 검증에서 확정, 00 v1.32·01 v1.51). **① 예고된 처방을 그대로 베끼지 않았다** — [[DEC-20260813-bsjeong87-02]] 계열로 PROJECT_PLAN에 적어 둔 "1회 재발하면 00 ③에 셋째 증거 경로(**사용자 확인**) 배선"이 오늘 발동했는데, 실제 재발 사례(wave 아카이브 대기)는 **파일 줄 수와 포인터로 즉시 관찰됐다**. 사용자에게 물었다면 자기신고를 증거로 삼았을 것이고, 이는 같은 절 바로 위가 "자기신고만 믿지 말고 §검증 명령으로 확인한다"고 한 것과 정면으로 어긋난다. 그래서 **`직접 확인 → 관찰 불가면 질문`** 순으로 뒤집어 넣었다. **관찰 시점의 처방 설계는 가설이고, 집행 시점엔 실물 사례가 손에 있다** — 예고를 이행 의무로 읽으면 그 사이에 얻은 정보를 버리게 된다. **② 근거가 갈리는 곳엔 처방하지 않는 쪽을 골랐다** — 혼합형의 비-git 단위(`wave-local`)가 기록을 자체 `docs/`에 두는지 상위 repo의 `docs/<단위>/`에 두는지 §B와 §F-2 C가 서로 다르게 읽히지만, **두 읽기 모두 정당하고 실제로 기록이 갈린 사례는 0건**이다. 한쪽을 못 박으면 나머지 환경이 깨진다 — [[DEC-20260812-bsjeong87-15]]가 "회귀 다수가 직전 추가가 만든 것"이라 한 것의 예방 적용으로, **관찰로 등재하고 사례가 생기면 고정**한다. **③ 사본은 세고 시작한다** — 어제의 자작 회귀(R21·R22를 A에만)를 되풀이하지 않으려고 이번엔 편집 **전에** `기록 체계 미설치` 문구를 grep해 4벌(§F-2 A·B·C + 실물 스킬)을 확정하고 들어갔다. `check.ps1`은 파일 단위라 여기서도 눈이 멀지만, **세고 시작하는 것**은 사람이 할 수 있다. **④ 내 발견도 재검증 대상이다** — "STEP 2 지시가 소실됐다"는 발견은 `cut`으로 잘린 출력을 근거로 한 오탐이었고 git 이력 대조로 기각했다. `/audit` §2가 에이전트 보고에 요구하는 재검증은 **내가 직접 찾은 발견에도 똑같이 적용된다**.

- **DEC-20260821-bsjeong87-03** — **마커 검사는 파일 단위라 "한 파일 안 여러 사본"을 못 잡는다 + 시나리오는 서로 다른 경로를 밟아야 회귀를 드러낸다**(sfa형 시나리오 검증에서 확정, 00 v1.31·01 v1.50·`RULES.md` 읽는 법 보강). 배경: 같은 날 nastvad형 반영을 커밋한 **직후** sfa형을 돌렸더니 **첫 발견이 그 커밋의 회귀**였다 — R21·R22를 `§F-2` **A 템플릿에만** 넣고 B·C를 빠뜨렸는데 `check.ps1`은 OK를 냈다. **① 검사의 구조적 한계다** — `RULES.md`의 필수 목록은 *파일 코드*(`01`·`RC`·`~wrap`)로 되어 있고 검사는 파일에 마커가 있는지만 본다. 그런데 `01 §F-2`는 스킬 **설치 페이로드**라 같은 규칙이 A·B·C 세 벌로 존재한다([[DEC-20260813-bsjeong87-01]]이 "사본은 범용성의 비용"이라 한 그 사본이 **한 파일 안에** 있는 경우다). 파일 단위 검사로는 원리적으로 못 잡으므로 **검사를 늘리지 않고 사람 체크리스트로 넘겼다** — 읽는 법에 "마커는 파일 단위"를 명시하고 해당 규칙 열에 파일 안 사본 위치를 병기. 판단이 필요 없는 것만 담는다는 `check.ps1`의 경계를 지킨 선택이다. **② 시나리오의 값어치는 "다른 경로를 밟는가"에 있다** — nastvad형은 단일 repo라 A 경로만 지나 이 결함을 통과시켰고, sfa형이 B·C를 밟자마자 드러났다. [[DEC-20260812-bsjeong87-14]]가 "회귀 감사와 전수조사는 다른 도구"라 한 것의 확장으로, **같은 축을 두 번 도는 것보다 다른 축을 한 번 도는 것이 낫다**. **③ 정책 전환기가 결함을 활성화한다** — S6(위임 표기의 정본 부재)과 S5(A/B/C 상위집합 미명시)는 둘 다 **root 폐지 전환기**에 흔해진다. 전자는 위임이 달린 하위 repo만 클론한 팀원에게 그 문서가 영영 안 깔리는 문제고(정본 없는 위임은 "적용됨"이 아니라 **확인 불가**), 후자는 A·B·C가 섞이는 기간에 **글로벌이 PC당 하나**라 고를 근거가 없던 문제다(실제로는 C ⊃ B ⊃ A). **정책 변경은 새 결함을 만들지 않지만 잠자던 결함을 깨운다** — [[DEC-20260821-bsjeong87-02]]가 "정책이 구조 축을 지운다"고 했을 때 계산에 없던 비용이다.

- **DEC-20260821-bsjeong87-02** — **팀 정책과 문서 개정은 대립항이 아니다 — 정책이 구조 축을 지우고 문서가 사람 축을 처리하며, 문서 한 줄이 그 정책을 배포한다**(root 폐지 채택, 01 §E-2 권장 기본값). 배경: 사용자가 "root 폐지가 답이면 팀에 지시하면 되고, 아니면 문서를 고치면 되는데 판단이 어렵다"고 물었다. 넷을 비교해 갈렸다 — **①정책만은 nastvad가 반증**한다(이미 root 없는 단일 repo인데 병합 문제가 거기서 나왔다. "이미 그 대안대로 사는 사례"를 찾으면 추상 논쟁을 건너뛴다) **②문서만**은 §F-2 C 간섭(한 PC의 통합형 스킬이 다른 솔루션 세션까지 지배)을 남긴 채 root 분기 전부를 전순위로 손봐야 해 작업량 최대 **③전원 root 표준화**는 가장 검증 안 된 경로(§E-4·§F-2 C — "B 폴백은 만들어본 적 없다"가 미해결로 남아 있는 자리)를 전원 필수로 만든다(**통일 자체는 미덕이 아니다 — 어느 쪽으로 통일하느냐가 전부**) **④정책+문서**가 이긴다. 문제가 **구조 축(폴더 배치)과 사람 축(동시 인원)** 둘인데 정책은 앞만 건드리고, 정책이 먼저 서면 문서 작업의 절반(소유 축)이 하향된다. **범용 배포물이라 분기는 줄지 않는다** — 팀이 root를 안 써도 §E-4는 못 지운다(다른 조직은 쓴다). **팀 운영 복잡도와 문서 분기 수는 별개 축**이고, root 폐지는 앞만 낮춘다([[DEC-20260813-bsjeong87-01]] "사본 수는 범용성의 비용"과 같은 축 — 처방은 삭제가 아니라 **전제를 정확히 적는 것**). 강제 전환은 불요로 판정 — §E-4 불침습이 층 간섭을 0으로 만들어둬 마이그레이션 문제가 성립하지 않고, 기록 정본이 처음부터 말단에 있어 전환이 사실상 공짜다(상위는 파생 인덱스뿐). 점검 대상은 "누가 root를 쓰나"(명단)가 아니라 **"누구의 root가 경계를 넘었나"**(공유 repo 커밋 / 폴백 없는 C) 둘뿐이다. **뒤집히는 조건**: "열람" 수요가 실증되면 공유 인덱스(=회사 root repo)가 재부상 — 지금 결정이 그 길을 막지 않는다.
