    Chapter 0 · about 2 minutes

    The choices the installer offers,
    learned by clicking them

    Drop this repository’s documents into a project, say “read this and apply it”, and Claude asks you to make a few choices. This course recreates those questions as the real screens and shows you, right there, what gets created and what changes for each option.

    • The chapters are built to be read in order, but you can jump around with the contents on the left.
    • When a simulator appears, click through it. It sticks far faster than reading alone.
    • Your progress is stored in this browser only. Nothing is sent to a server.
    📖
    The dictionary to look things up, this course to learn the shape The same material is organized item by item in the install options dictionary. Mid-install, when you think “what is this?”, the dictionary is faster; for the whole picture the first time, this course is better.

    Chapter 2 · how an install flows

    Across five steps, questions come at only two of them

    Claude investigates before it asks. Anything the files can answer — what is already installed, whether this is git, which language the code is in — is never asked; only what the code cannot tell it. And every choice carries a one-line note on what you get if you pick it · what happens if you don’t. Click each step for detail.

      📌
      Most detailed questions appear only in “custom” mode In minimal, recommended and full, the per-document items are settled automatically at that mode’s defaults. There are two exceptions: items that are off by default are always asked, bundled into one round, and items that mode has no default for are never settled silently — they are put to you as they are (pick minimal mode with only the “stronger verification” bundle on top, for instance, and all three parts of 04 come up as questions). The safety questions (“overwrite what is already here?”, “have you checked company policy?”) are never skipped, in any mode.

      Chapter 4 · the second big choice

      Purpose bundles — layered on top of the mode

      A bundle is unioned onto the base mode. Pick “recommended” + “design” and the design extensions land on top of whatever recommended selected. Toggle several on and off.

      The real install screen shows at most four choices per question, so when there is more to pick from — bundles, for instance — the question is split into several. Nothing gets squeezed into one box or dropped for lack of room.

      In a real install, bundles that match what was detected come already ticked — design for a frontend stack, stronger verification when tests or CI exist, feature documentation when a feature-spec folder exists. Answer that this is a company repository and the company bundle applies automatically. Unattended automation and answer style cannot be detected, so you pick them only when you want them. App screen verification appears only for a Flutter app project, and it is marked as recommended but never ticked in advance — it adds a dependency to the app’s pubspec.yaml, so the choice is left to you. If the project is not Flutter, the bundle does not appear. Operations works the same way: when Claude finds signs that the project gets deployed (a hosting config file such as Dockerfile or vercel.json, a CI workflow with a deploy step, a deploy script), it is marked as recommended but never ticked in advance — the skill can write code into your app, so the choice is left to you. It does not appear for documentation-only repositories.

      Chapter 5 · the remaining common questions

      Operating profile, usage pattern, output language, name alias, and what is already there

      Quick path — only on an already-set-up PC

      The question that comes first, and only when this PC already has an install record but this project does not have one yet. It shows the PC name from that record and asks you to confirm it is this PC first (answer no and the shortcut folds away and each question is asked). It does not appear when you cloned a repo a teammate already set up, or when re-applying — so the team’s settled values are never overwritten by your PC’s. It is not a new mode — it is a shortcut for answering the common questions in one go (base mode, bundles, profile, usage pattern, language, alias). Whichever you pick, the values it will carry over are shown and you confirm them.

      • This PC’s defaults (default pick) — uses the profile (and language and alias, if recorded) already settled on this PC and goes with mode Minimal (plus in-work suggestions). The values are shown and you only confirm. Anything this PC has no value for is asked as its own question — the usage pattern is never in this PC’s record, so that one is always asked. From the second project on the same PC, this one.
      • Same as another project — carries over the mode, bundles, usage pattern, language and alias recorded in another project on this PC. Only the profile comes from this PC. Only projects that actually exist now and have an install record are offered, and which project the values came from is not written to the record (this project’s record is shared with the team).
      • Recommended mode — the Recommended mix Claude puts together by looking at this folder alone, plus defaults.
      • One by one — no shortcut; you get the common questions from the start, all of them.
      📌
      The quick path only shortens the common questions The safety questions (“may I overwrite what is already there?”), the existing-team-setup question below, the company-policy check, the scope questions about where things should live, and the questions about items that are off by default still appear. Not even the “everything” mode can skip those, so a shortcut must not either.

      Operating profile and usage pattern — two separate questions

      The operating profile is about your plan’s allowance and belongs to this PC. The usage pattern is about how this project is run (several agents at once, a standing team of role agents, runs with nobody watching) and is shared with the team. If a value is already recorded — the profile in this PC’s global record, the usage pattern in this project’s record — it is shown and you only confirm it.

      Where the answers are kept, and changing them later

      The profile goes into this PC’s global record (~/.claude/CLAUDE.md). The usage pattern goes into this project’s record as 형태= — pick none and it reads 형태=단일 (single), pick several and they are joined with +. It is shared with the team because it shapes files everyone commits, such as the agent roster and the hand-off rules. It is asked only when you install into a project, not for a PC-only install. A project record written before this question existed reads as 형태=단일, and the next re-run asks it once.

      What the folder already holds can mark a pattern as recommended — agents set to isolated worktrees (parallel), several role agents beyond the 02 roster (role team), a routines record or claude -p in CI (unattended) — but it is never ticked for you. Neither answer creates files on its own: they only change what comes pre-checked or suggested in the lists you still pick from. If the two pull different ways, the allowance wins — thrift with parallel keeps the thrift-sized fan-out.

      If you change either answer when it is shown for confirmation on a re-run, the same table below follows. To change either later, run /dropin-pick 프로필. It asks again with your current values, shows a table of what would change in what is already installed (read from the actual files, not just the record), and you approve it row by row — keep is the default, and a newly suggested item (agent-guard after switching to parallel, say) goes to its own item question instead of being installed. Changing the profile edits this PC’s setup by default; changing the usage pattern, or approving a row on a committed agent roster, changes files the team shares, so you are reminded to commit.

      Output language — Korean / English

      This one is easy to misread: it is not the language of the documents but the language of what the install produces. The drop-in documents stay Korean — Claude executes them identically either way — while your answer here decides the language of the target CLAUDE.md body, the docs/ entries, commit messages and generated filenames (docs/difficulty-matrix.md vs docs/난이도-매트릭스.md). Format keywords such as [topic][Done] stay fixed in either language, because /resume and /wrap find them by those exact strings. The default is the language you are chatting in, and if outputs already exist, their language comes first.

      Skill name alias — none / all / selected only

      The skill names being installed (resume, wrap, svg-design) are common ones. If a different skill of the same name already sits on your machine, that one wins — the install reports success but the wrong thing runs, or what you were using gets buried. This question is the way out: attach the nickname Dandi to get dandi-resume (prefix) or resume-dandi (suffix). If you choose to attach one, it goes on to ask for the text (default dandi) and the position (prefix/suffix); with selected only you tick the skills from the install list yourself. None is the default — the installer looks for collisions first, and if it finds any it suggests “selected only” with just those skills ticked. The six feature-doc skills call each other by name, so they move together. On a re-run the recorded alias is reused without asking again. If the record and the names installed on this PC differ, you are asked whether to rename this PC’s to match, install one more under the alias (the same skill then appears under two names), or keep an exception for this PC only. Installing frontend-design, session-board or agent-guard as a plugin attaches no alias — to have one, pick another install path. Details in the options dictionary, 2-7.

      If something is already installed — keep / reconcile / replace

      Asked for every item where existing settings are detected — always, whatever the mode. Click to see the difference.

      The exception in how it is asked: global items already on this PC (settings every project shares) are bundled into one question so you do not answer the same thing every time you set up a project — the list is shown and the default is keep. Only the ones you answer reconcile or replace for are split out and asked one by one. An item touched by a change you approved during a re-run defaults to reconcile.

      If the team has a committed Claude setup — team setup first / item by item

      Asked only on the first install (no install record yet), when the repository already has a Claude setup the team committed (CLAUDE.md, .claude/CLAUDE.md, AGENTS.md, .mcp.json, settings, skills or agents under .claude/ and so on). Files that exist only on your machine and were never committed do not count. Once a record exists, the setup it finds is not judged again — much of it may be what the earlier install itself committed.

      • Team setup first (recommended when detected) — every overlapping item is treated as keep and the team’s files are not edited. An item that would need a team file changed is not installed — it is noted in the record as not chosen, and later runs and in-work suggestions do not offer it again while this answer stands (switch to item by item to lift that). Items that only add new files go ahead, with a note that committing them needs the team’s agreement. The one exception is the install-record line itself, which is still written into CLAUDE.md; until the team agrees to commit it, it stays uncommitted, so /resume only fetches instead of pulling and /wrap warns about it each time.
      • Decide item by item — asks keep / reconcile / replace (above) for each overlapping item.

      Your answer is saved in the install record the team shares. When you run it again, or a teammate joins, that value is shown and you only confirm it. The quick path above does not skip this either — so a newcomer’s defaults never overwrite what the team agreed on. In a company setting (the company bundle, or an organization approval check) it also checks for managed settings your company pushed out — it asks you to look at the Setting sources line in /status, and any item that would clash with them is not installed, with a note why (no choice can override managed settings).

      Chapter 7 · items inside a document ②

      For development projects — 02 split · 03 add-ons · 04 verification

      Three documents that only mean something where there is code. Expand them one at a time.

      02Model split — expensive and cheap models, divided development only

      Installs a subagent roster that sends hard analysis and design to the stronger model and well-defined repetitive work to the cheaper one. Push hard work onto a cheap model to save money and you get results that are almost right but wrong, and the rework costs more — which is why the triage itself always uses the stronger model.

      AgentWhat it doesModel
      surveyorSweeps the structure broadly and mechanically into a list (no judgments)sonnet
      triageScores that sweep for difficulty — the seat that matters mostopus
      analystAnalyzes the hard parts and writes the implementation specby difficulty
      spec-writerPins down requirements for a new feature — step one of building something newopus
      implementerBuilds to the spec (nothing outside scope)sonnet
      parity-testerRuns the tests and reports pass/diff onlyhaiku

      Agents are chosen one at a time, not as a block. Changing existing code → the five without spec-writer; building something new → drop surveyor and triage and start from spec-writer. A custom reviewer is offered as well, but it starts unchecked — the built-in /code-review already covers correctness review.

      Each agent file also carries its reasoning effort next to the model, so you do not pick it every time you call one. You are also asked whether the roster is shared with the team (committed to the project) or just for you (your machine). If no test command is detected, parity-tester starts unchecked — it would have nothing to run. If you later re-fit agents with agent-tune (03), re-applying this roster keeps the model and effort it recorded instead of putting the template values back.

      The same list offers a difficulty rubric and a hand-off document that fixes which agent follows which and what each passes on. On a large project whose pieces are independent, you are also offered running implementers in parallel, each in its own isolated worktree — set permanently in the agent file, or only when called, in which case the rule is written into the hand-off document (skip the hand-off document and it goes in the agent file; a roster kept just for you is not offered parallel running at all). Choose the parallel usage pattern and setting it only when called is the default suggestion (the permanent setting stays an option), with the hand-off document pre-checked.

      There is one more optional item (unchecked by default) — a /plan-<model> command that runs a different model only while planning. When the plan is done it returns to your normal model by itself. Where that command lives (just for you on your machine, or shared with the team in the project) is asked separately from the roster. You are also asked whether it should run only when you call it, and a usage table of which model takes which work (docs/model-usage-table.md) is created with it.

You choose whether to install it as a dandi plugin or as a copied file (if both are found, the count runs twice, so you are asked to keep one), and you are asked separately whether to also cap workflow agents at the same number for this PC.
      • agent-tune (per-agent model tuning) — gives each helper agent (subagent) in a project the model and reasoning effort that fit its job. It reads the agent files (the project’s .claude/agents/ and your machine’s ~/.claude/agents/), shows what each one does and runs on today, asks only what the files cannot tell (how often it runs, whether its results have had problems and why, and whether you put quality or cost first), reads your operating profile as a limit on the model, and proposes a model and effort per agent with a one-line reason and a cost trend. Model names, prices and effort levels are looked up in the official docs on the day it runs. Only the agents you approve change, and only their model: and effort: lines — it never creates or deletes agents. What it set, and the values it replaced, go into an assignment record (docs/에이전트-배정.md, or docs/agent-assignment.md for English output); re-applying the 02 roster keeps those values instead of resetting them. /agent-tune 점검 (check) compares the record with the files without changing anything, and /agent-tune 되돌리기 (revert) restores the previous values. It edits agent files, so it starts unchecked and is in no bundle — on a role-team usage pattern it is marked as suggested, still not ticked. Its scope defaults to your whole machine (it looks at the agents of whichever folder you call it from), and by default it runs only when you type /agent-tune.
      • tool-tune (tool version check) — keeps the tools Claude works with on this PC current: tools for driving screens and browsers, controlling desktop apps, verification and doc lookup (MCP servers, plugins, global npm and Dart tools, and winget or brew packages on Windows and macOS). It reads what is installed, compares it with the registries and official releases on the day it runs, and shows only what differs in one table. When a better tool for the same job exists, it suggests installing it alongside the old one, with the official link and the date it checked — tools these documents have already ruled out are never suggested, and if the suggestion is a new MCP server or browser tool, it asks the same company-approval questions first. Only what you approve is updated or installed, and the previous version and the command to go back are kept in ~/.claude/tool-tune/log.md. /tool-tune 점검 (check) only reports, and /tool-tune 되돌리기 (revert) returns to the recorded previous version. Your project’s own dependencies (linters, test runners) are only reported, and Claude Code itself is left to its own auto-update. It updates and installs machine-wide tools, so it starts unchecked and is in no bundle. Its scope defaults to your whole machine, and by default it runs only when you type /tool-tune. On a work PC, check the policy on updating and installing software first.

      Choosing a skill brings two more questions — scope (your whole machine vs. this project only) and invocation (Claude decides vs. only when you type /command). Policy notes and the feature change log (this project only) and session-board, agent-guard and the diff review tools (whole machine) have a fixed place, so their scope is announced, not asked. For Flutter app screen verification the MCP server is registered either just for you in this project or shared with the team (there is no whole-machine option). If the feature-doc set, refactor, kr-ui-guide, browser-check, pc-clean, ops-kit, win-setup, knowledge base set, agent-tune or tool-tune is already turned on as a dandi plugin, it also asks whether to keep the plugin (no copy) or replace it with the copy — never both. Session-board and agent-guard are asked about separately, when their hooks would run twice.

      Pick frontend-design or kr-ui-guide and one more question follows — a font licence policy, written into the CLAUDE.md of the scope you installed into. Free fonts only (the default) turns down any font that is not free to use and offers a free alternative instead; tell me the terms first explains the conditions and waits for your call; skip it writes no policy at all. One policy covers whichever design skill you end up using — frontend-design on its own does not look at licences, and it is the one that changes typography most eagerly. Scope, font policy and browser tools are asked in every mode — no mode settles them for you.

      💡
      Asked for approval every time a policy note or feature-log line is written? Both write under .claude/, which Claude Code treats as a protected folder. In the default mode and the accept-edits mode each write asks for your approval; in a non-interactive -p run outside auto mode or dontAsk mode it is refused; an allow rule does not lift that. Auto mode and bypassPermissions let it through. The install tells you this when you pick either item.
      🔴
      At work MCP can send your conversation outside, and a connected browser can reach your logged-in sessions. Flutter app screen verification adds an outside package to the app’s dependencies and registers an MCP server. Connect only servers your organization allows, and narrow the extension’s site permissions to localhost.
      💡
      Not sure whether this counts as a company repository? Say you don’t know. For MCP servers, browser verification, Flutter app screen verification, the 04 CI integration and 06 routines, “don’t know” is treated as a company repository: that item (for 06, the whole document) is held back until it is approved, the rest still installs, and this PC’s install record notes why. Once approval comes, the next re-run asks about it again.
      04Verification — machine checks instead of “it’s done” the hook gate is the core
      • Hook quality gate — a linter or syntax check runs every time Claude edits a file, and the failure output goes back to Claude, which fixes it itself. Never dropped, even on the thrift profile — less rework is the biggest saving there is. Choosing it also asks for the scope (team-shared / your whole machine / just you, this project only) and the strength: block (the default) does not undo the edit — the failure goes back to Claude, which keeps fixing until it passes; warn only just shows you a notice, and Claude does not see it. If a gate you already have is the old kind that cannot hand failures back to Claude, you are told so and reconcile is suggested (keeping it is fine for a hook that only auto-fixes with a formatter).
      • Host CLI (gh/glab) — lets Claude open PRs and read CI failure logs directly. You sign in yourself. With no remote yet, the CLI and CI are left out and only the hook goes ahead; the next re-run asks again once a remote exists.
      • CI integration — mention @claude on a PR and it reviews or fixes — on GitHub this starts working once the setup workflow is merged into the default branch. GitLab’s official integration runs from manual and merge-request pipelines, and mentions need a listener you set up yourself; other hosts call Claude from a CI stage. 🔴 org approval required at work — CI sends your code to the Anthropic API. Pick it and, along with whether this is a company repository, whether you checked the policy and whether it is approved, you are asked in the same place about admin rights, how secrets may be registered, the app’s permission scope and cost (runner time and tokens) — only what applies to the detected host. Without approval only CI is left out; the rest installs.

      Slow tests do not go in the hook — minutes on every edit makes the session sluggish. That is CI’s job.

      Chapter 8 · items inside a document ③

      05 output styles · 06 routines

      05Output styles — changing Claude’s tone and role optional

      Pick one of the built-ins (Default, Proactive, Explanatory, Learning, Concise — the /config menu shows whatever is there on the day), or write the role and tone you want into a single markdown file. While you are learning, Explanatory — which explains why it did things that way as it goes — is the useful one.

      Switching a built-in and writing your own both come unchecked — tone is a matter of taste, so no mode picks for you. Write your own and you are also asked whether to turn it on now (making it and leaving it off is fine too); pick both and only one style can be on, so you choose which one.

      When you write your own, you are asked separately where the style file lives (your whole machine / this project) and where the switch-on setting goes (just you, this project / your whole machine / the whole team) — a file placed machine-wide still stays off in other projects if the setting only lives in this one.

      🔴
      The custom-style trap — keep-coding-instructions It defaults to false, and where the full system prompt is in use, false makes Claude Code’s entire built-in coding guidance disappear (verification habits and the minimal-change principle included). Models that default to a short system prompt do not have that section, so there the value makes no difference. If you will also be coding with the full prompt, set it to true.

      One more thing — switching a style takes effect from your next message (v2.1.251+). Only editing a style file needs a restart, because files are read at startup.

      06Routines — cloud jobs that run with your PC off gates first

      Scheduled jobs that run unattended in the Anthropic cloud — nightly PR review, weekly doc checks, that sort of thing. (The official name is now scheduled tasks; the /schedule command is unchanged, and these documents keep saying “routines”.) Before installing, the following is always asked, because the code cannot answer it.

      • ① Is your plan Pro or above (and is GitHub connected to your claude.ai account)?
      • ② For a company repository — does your organization permit cloud execution (code leaving the building)? On Team and Enterprise plans, is the Scheduled tasks switch in the admin settings on (only the Owner can change it)?
      • ③ Is it a GitHub repository? (GitHub only, for now — if not, it is recorded as “not applicable” and not asked again)
      • ④ Is the job safe to run unattended? — nobody is watching: a new run starts in auto mode, where a classifier decides what goes ahead, and a result artifact can be published without asking (only you can see it until you share it), so nothing hard to undo (deploys, deletions, outbound messages) goes in it
      • ⑤ Does the /schedule command actually show up? If a requirement is unmet it is usually hidden, as if it did not exist

      Past the gates, these are the items: repo preparation (what the cloud run needs, such as a committed .mcp.json), creating the routine (unchecked by default — once created it starts running and using your allowance; you are asked what it is for and which trigger runs it: schedule, API or GitHub event) and a definition record in docs/ROUTINES.md. Pick routine creation and the other items come checked. On the thrift profile it suggests a cautious frequency, starting weekly.

      💡
      If it needs files on your machine, it is not a routine Routines run in the cloud, where your files do not exist. Use them only for “must run with the computer off”.

      Chapter 10 · after the install

      Keeping it current

      Installing once is not the end of it. The documents get revised, and so do the skills they install. Each command below answers a different question — and confusing them is the usual reason people keep running a stale setup.

      You want to…CommandWhat changes
      Find out whether anything fell behind/dropin-checkNothing — it reads and reports
      Refresh your copies of the documents/dropin-updateThe document files only
      Bring the configuration itself up to date/dropin-applyDocuments, installed skills, settings
      Do all three in order/dropin-syncWhatever the three would change — each asks where it asks
      Install just one kind of thing (only MCP, only plugins…)/dropin-pickOnly the items of the kinds you pick — each still asked, off-by-default ones still off
      Change the operating profile or usage pattern later/dropin-pick 프로필Nothing new is installed — you see what would change in what is already there and approve row by row (keep is the default)

      The one thing people get wrong

      /dropin-update on its own is not an update. It refreshes the instruction manual, not the thing the manual builds. Your installed skills and settings stay exactly as they were until /dropin-apply runs.

      On a machine you have not set up yet

      /dropin-apply is also the first-install command, so you never have to work out which case you are in. If the command does not exist there yet, say it in words instead: “read 00_핸합-설치.md from the repository and apply it to this machine” — and the command arrives with everything else.

      What re-applying shows you

      Re-running lists what changed since your recorded version, document by document, one row per version, and you approve row by row — only approved rows get installed (a row that sums up an older stretch of versions counts as one). A row you hold back is noted in the install record, so it comes up again next time instead of vanishing. If your record is old enough to fall inside a summary row, you are also asked whether to re-apply that whole document.

      Even when versions match, three things are asked: whether to check for anything out of line; whether to add what you skipped or take out what is installed (each skipped document is shown in one line); and whether anything blocked or left waiting last time (sign-in pending, org approval, a document that could not be fetched) has cleared. If it has, it gets installed; if you no longer want it, it switches to not chosen so the question stops repeating. Things recorded as not applicable or declined in an in-work suggestion are not offered again — declined ones you can still add yourself on a re-run.

      Running it for the first time on this PC in a repository a teammate already set up counts not as a re-apply but as joining. Following the repository’s setup (keep) is the default, and global items missing from this PC (commands like /resume and /wrap) go on the install list whatever the version. Items that are off by default are shown still off.

      Why a name check is not enough

      A skill can be revised without gaining or losing a single file — only its wording changes. A check that compares file names calls that “already current”. The install steps compare file contents as well, which is why a wording-only revision still reaches your disk.

      💡
      Re-running stops and says the record is newer than your documents? That happens when another PC or a teammate already installed with newer documents than the copy on this machine. Carrying on would overwrite the setup with the older procedure, so Claude updates the documents first and then starts the re-apply again. If the documents cannot be fetched, only that document is skipped, and a note stays in this machine’s record so the next run tries again.

      Three things to remember

      • First time? Minimal mode — start light and add the rest when it is suggested during your work, picking only what you want (or call /dropin-apply 추천 yourself).
