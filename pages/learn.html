    Chapter 0 · about 2 minutes

    The choices the installer offers,
    learned by clicking them

    Drop this repository’s documents into a project, say “read this and apply it”, and Claude asks you to make a few choices. This course recreates those questions as the real screens and shows you, right there, what gets created and what changes for each option.

    • The chapters are built to be read in order, but you can jump around with the contents on the left.
    • When a simulator appears, click through it. It sticks far faster than reading alone.
    • Your progress is stored in this browser only. Nothing is sent to a server.
    📖
    The dictionary to look things up, this course to learn the shape The same material is organized item by item in the install options dictionary. Mid-install, when you think “what is this?”, the dictionary is faster; for the whole picture the first time, this course is better.

    Chapter 2 · how an install flows

    Across five steps, questions come at only two of them

    Claude investigates before it asks. Anything the files can answer — what is already installed, whether this is git, which language the code is in — is never asked; only what the code cannot tell it. And every choice carries a one-line note on what you get if you pick it · what happens if you don’t. Click each step for detail.

      📌
      Most detailed questions appear only in “custom” mode In minimal, recommended and full, the per-document items are settled automatically at that mode’s defaults. There are two exceptions: items that are off by default are always asked, bundled into one round, and items that mode has no default for are never settled silently — they are put to you as they are (pick minimal mode with only the “stronger verification” bundle on top, for instance, and all three parts of 04 come up as questions). The safety questions (“overwrite what is already here?”, “have you checked company policy?”) are never skipped, in any mode.

      Chapter 5 · the remaining common questions

      Operating profile, output language, name alias, and what is already there

      Quick path — only on an already-set-up PC

      The question that comes first, and only when this PC already has an install record but this project does not have one yet. It shows the PC name from that record and asks you to confirm it is this PC first (answer no and the shortcut folds away and each question is asked). It does not appear when you cloned a repo a teammate already set up, or when re-applying — so the team’s settled values are never overwritten by your PC’s. It is not a new mode — it is a shortcut for answering the common questions in one go (base mode, bundles, profile, language, alias). Whichever you pick, the values it will carry over are shown and you confirm them.

      • This PC’s defaults (default pick) — uses the profile (and language and alias, if recorded) already settled on this PC and goes with mode Recommended. The values are shown and you only confirm. Anything this PC has no value for is asked as its own question. From the second project on the same PC, this one.
      • Same as another project — carries over the mode, bundles, language and alias recorded in another project on this PC. Only the profile comes from this PC. Only projects that actually exist now and have an install record are offered, and which project the values came from is not written to the record (this project’s record is shared with the team).
      • Recommended mode — the Recommended mix Claude puts together by looking at this folder alone, plus defaults.
      • One by one — no shortcut; you get the common questions from the start, all of them.
      📌
      The quick path only shortens the common questions The safety questions (“may I overwrite what is already there?”), the company-policy check, the scope questions about where things should live, and the questions about items that are off by default still appear. Not even the “everything” mode can skip those, so a shortcut must not either.

      Operating profile — standard / thrift

      Q. Choose an operating profile

      ⚙️ What changes

      Pick a profile on the left.

      Output language — Korean / English

      This one is easy to misread: it is not the language of the documents but the language of what the install produces. The drop-in documents stay Korean — Claude executes them identically either way — while your answer here decides the language of the target CLAUDE.md body, the docs/ entries, commit messages and generated filenames (docs/difficulty-matrix.md vs docs/난이도-매트릭스.md). Format keywords such as [topic][Done] stay fixed in either language, because /resume and /wrap find them by those exact strings.

      Skill name alias — none / all / selected only

      The skill names being installed (resume, wrap, svg-design) are common ones. If a different skill of the same name already sits on your machine, that one wins — the install reports success but the wrong thing runs, or what you were using gets buried. This question is the way out: attach the nickname Dandi to get dandi-resume (prefix) or resume-dandi (suffix). If you choose to attach one, it goes on to ask for the text (default dandi) and the position (prefix/suffix); with selected only you tick the skills from the install list yourself. None is the default — the installer looks for collisions first, and if it finds any it suggests “selected only” with just those skills ticked. The six feature-doc skills call each other by name, so they move together. Details in the options dictionary, 2-7.

      If something is already installed — keep / reconcile / replace

      Asked for every item where existing settings are detected — always, whatever the mode. Click to see the difference.

      The exception in how it is asked: global items already on this PC (settings every project shares) are bundled into one question so you do not answer the same thing every time you set up a project — the list is shown and the default is keep. Only the ones you answer reconcile or replace for are split out and asked one by one.

      Chapter 7 · items inside a document ②

      For development projects — 02 split · 03 add-ons · 04 verification

      Three documents that only mean something where there is code. Expand them one at a time.

      02Model split — expensive and cheap models, divided development only

      Installs a subagent roster that sends hard analysis and design to the stronger model and well-defined repetitive work to the cheaper one. Push hard work onto a cheap model to save money and you get results that are almost right but wrong, and the rework costs more — which is why the triage itself always uses the stronger model.

      AgentWhat it doesModel
      surveyorSweeps the structure broadly and mechanically into a list (no judgments)sonnet
      triageScores that sweep for difficulty — the seat that matters mostopus
      analystAnalyzes the hard parts and writes the implementation specby difficulty
      spec-writerPins down requirements for a new feature — step one of building something newopus
      implementerBuilds to the spec (nothing outside scope)sonnet
      parity-testerRuns the tests and reports pass/diff onlyhaiku

      Agents are chosen one at a time, not as a block. Changing existing code → the five without spec-writer; building something new → drop surveyor and triage and start from spec-writer. A custom reviewer is offered as well, but it starts unchecked — the built-in /code-review already covers correctness review.

      Each agent file also carries its reasoning effort next to the model, so you do not pick it every time you call one. You are also asked whether the roster is shared with the team (committed to the project) or just for you (your machine).

      There is one more optional item (unchecked by default) — a /plan-<model> command that runs a different model only while planning. When the plan is done it returns to your normal model by itself. Where that command lives (just for you on your machine, or shared with the team in the project) is asked separately from the roster.

      ⚠️
      Not installed in a repository with no code A roster in a documentation-only place just adds files nobody uses. Claude detects that and tells you.
      03Add-ons — status line, design skills, MCP, browser, feature docs, refactor, Korean UI guide all optional
      • claude-hud — a status line under the input box showing context and plan usage. Practically required on the thrift profile.
      • svg-design — a rulebook for implementing SVG effects (hand-drawn, Gooey, glass, neon) correctly. For projects that build web screens.
      • frontend-design — an official Anthropic skill that steers away from UI that looks AI-generated.
      • MCP servers — connect external tools (GitHub, doc search, browser control). Which servers to attach is asked separately.
      • Browser verification — lets Claude open the screens it built, check them and fix them.
      • Feature-doc skill set (6 skills) — writes a spec per feature from the code and the real screen, then runs the tests written in it, blocks commits that skip the doc, and builds release notes. Installed as one set; not for documentation-only repositories. The commit guard, which blocks every teammate’s commits, starts unchecked and is asked about separately.
      • refactor — cleans up code (merging duplicates, tidying structure, clearing dated syntax) and then proves the behaviour did not change — call sites, contracts, data formats, an actual test run. Shows you the candidates and only changes what you pick. Not for documentation-only repositories.
      • kr-ui-guide — design rules from research on Korean services (UX patterns, icons, colour, recent design trends) and on Korean game UI/UX. Claude calculates contrast for the colours it proposes and checks screens against the checklists. For Korean-audience web, app and game screens; it does not copy any brand's look.

      Choosing a skill brings two more questions — scope (your whole machine vs. this project only) and invocation (Claude decides vs. only when you type /command). If the feature-doc set, refactor or kr-ui-guide is already turned on as a dandi plugin, it also asks whether to keep the plugin (no copy) or replace it with the copy — never both.

      Pick frontend-design or kr-ui-guide and one more question follows — a font licence policy, written into the CLAUDE.md of the scope you installed into. Free fonts only (the default) turns down any font that is not free to use and offers a free alternative instead; tell me the terms first explains the conditions and waits for your call; skip it writes no policy at all. One policy covers whichever design skill you end up using — frontend-design on its own does not look at licences, and it is the one that changes typography most eagerly.

      🔴
      At work MCP can send your conversation outside, and a connected browser can reach your logged-in sessions. Connect only servers your organization allows, and narrow the extension’s site permissions to localhost.
      04Verification — machine checks instead of “it’s done” the hook gate is the core
      • Hook quality gate — a linter or syntax check runs every time Claude edits a file, and the failure output goes back to Claude, which fixes it itself. Never dropped, even on the thrift profile — less rework is the biggest saving there is. Choosing it also asks for the scope (team-shared / your whole machine / just you, this project only) and the strength (block on failure / warn only).
      • Host CLI (gh/glab) — lets Claude open PRs and read CI failure logs directly. You sign in yourself.
      • CI integration — mention @claude on a PR and it reviews or fixes. 🔴 org approval required at work — CI sends your code to the Anthropic API.

      Slow tests do not go in the hook — minutes on every edit makes the session sluggish. That is CI’s job.

      Chapter 8 · items inside a document ③

      05 output styles · 06 routines

      05Output styles — changing Claude’s tone and role optional

      Pick one of the built-ins (Default, Proactive, Explanatory, Learning, Concise — the /config menu shows whatever is there on the day), or write the role and tone you want into a single markdown file. While you are learning, Explanatory — which explains why it did things that way as it goes — is the useful one.

      When you write your own, you are asked separately where the style file lives (your whole machine / this project) and where the switch-on setting goes (just you, this project / your whole machine / the whole team) — a file placed machine-wide still stays off in other projects if the setting only lives in this one.

      🔴
      The custom-style trap — keep-coding-instructions It defaults to false, and false makes Claude Code’s entire built-in coding guidance disappear (verification habits and the minimal-change principle included). If you will also be coding, set it to true.

      One more thing — switching a style takes effect from your next message (v2.1.251+). Only editing a style file needs a restart, because files are read at startup.

      06Routines — cloud jobs that run with your PC off gates first

      Scheduled jobs that run unattended in the Anthropic cloud — nightly PR review, weekly doc checks, that sort of thing. Before installing, the following is always asked, because the code cannot answer it.

      • ① Is your plan Pro or above (and is GitHub connected to your claude.ai account)?
      • ② For a company repository — does your organization permit cloud execution (code leaving the building)?
      • ③ Is it a GitHub repository? (GitHub only, for now — if not, it is recorded as “not applicable” and not asked again)
      • ④ Is the job safe to run unattended? — a routine never stops to ask for approval, so nothing hard to undo (deploys, deletions, outbound messages) goes in it
      💡
      If it needs files on your machine, it is not a routine Routines run in the cloud, where your files do not exist. Use them only for “must run with the computer off”.

      Chapter 10 · after the install

      Keeping it current

      Installing once is not the end of it. The documents get revised, and so do the skills they install. Three commands cover three different questions — and confusing them is the usual reason people keep running a stale setup.

      You want to…CommandWhat changes
      Find out whether anything fell behind/dropin-checkNothing — it reads and reports
      Refresh your copies of the documents/dropin-updateThe document files only
      Bring the configuration itself up to date/dropin-applyDocuments, installed skills, settings

      The one thing people get wrong

      /dropin-update on its own is not an update. It refreshes the instruction manual, not the thing the manual builds. Your installed skills and settings stay exactly as they were until /dropin-apply runs.

      On a machine you have not set up yet

      /dropin-apply is also the first-install command, so you never have to work out which case you are in. If the command does not exist there yet, say it in words instead: “read 00_핸합-설치.md from the repository and apply it to this machine” — and the command arrives with everything else.

      Why a name check is not enough

      A skill can be revised without gaining or losing a single file — only its wording changes. A check that compares file names calls that “already current”. The install steps compare file contents as well, which is why a wording-only revision still reaches your disk.

      Chapter 11 · wrapping up

      🎓

      Course complete!

      Three things to remember

      • Unsure? Recommended mode — Claude shows you why it combined things that way and asks you to confirm.
      • Whatever you choose, nothing is overwritten without approval, and secrets are neither read nor committed.
      • Skipping a checkbox is fine — run it again later and add it, or take out something already installed. The install record is there, so it picks up from where it was. Removal deletes only what the install created; the work records built up meanwhile are kept by default.
