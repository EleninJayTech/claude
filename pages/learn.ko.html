    • 챕터는 순서대로 보게 만들어져 있지만, 왼쪽 목차로 건너뛰어도 됩니다.

    챕터 2 · 설치의 흐름

    질문은 다섯 단계 중 두 곳에서만 나옵니다

    Claude는 묻기 전에 먼저 조사합니다. 파일로 알 수 있는 것(이미 설치된 것, git 여부, 사용 언어)은 묻지 않고, 코드로 알 수 없는 것만 물어봅니다. 각 단계를 눌러 자세히 보세요.

      📌
      세부 질문은 대부분 '사용자' 모드에서만 나옵니다 최소·권장·전체 모드에서는 문서 안 세부 항목이 모드가 정한 기본값으로 자동 확정됩니다. 예외는 둘입니다 — 기본으로 꺼져 있는 항목은 어떤 모드에서도 한 번에 묶어 물어보고, 그 모드에 기본값이 정해져 있지 않은 항목은 자동으로 정하지 않고 그대로 물어봅니다(예: 최소 모드에 '검증 강화' 번들만 얹으면 04의 세 항목이 전부 질문으로 나옵니다). 단, 안전 질문("이미 있는 걸 덮어쓸까요?", "회사 정책은 확인했나요?")은 어떤 모드에서도 생략되지 않습니다.

      챕터 4 · 두 번째 큰 선택

      목적 번들 — 모드 위에 얹는 것

      번들은 기반 모드에 합집합으로 더해집니다. 예를 들어 '권장'+'디자인'이면, 권장이 고른 것 위에 디자인 확장이 얹힙니다. 여러 개를 켜고 꺼 보세요.

      실제 설치 화면은 한 질문에 선택지를 4개까지만 보여 줍니다. 그래서 번들처럼 고를 게 많으면 질문이 몇 개로 나뉘어 나옵니다 — 칸이 모자란다고 한 칸에 묶거나 빼 버리지 않습니다.

      Q. 목적 번들을 골라 주세요 (0개 이상, 복수 선택)

      ➕ 얹히는 것

      아무것도 안 골라도 됩니다 — 그게 기본값입니다.

      🏢

      챕터 5 · 나머지 공통 질문

      운용 프로필, 산출물 언어, 이름 별칭, 그리고 이미 있을 때

      운용 프로필 — 표준 / 절약

      Q. 운용 프로필을 골라 주세요

      ⚙️ 달라지는 것

      왼쪽에서 프로필을 골라 보세요.

      산출물 언어 — 한국어 / English

      오해하기 쉬운 항목입니다 — 문서의 언어가 아니라 설치가 만들어 내는 것의 언어입니다. 드롭인 문서는 한국어 그대로 두고(Claude는 어느 언어로든 같게 실행합니다), 이 답이 대상 CLAUDE.md 본문·docs/ 기록·커밋 메시지·산출물 파일명(docs/난이도-매트릭스.md ↔ docs/difficulty-matrix.md)의 언어를 정합니다. [갈래][Done] 같은 형식 키워드는 어느 언어에서도 고정입니다 — /resume·/wrap이 그 문자열로 찾기 때문입니다.

      스킬 이름 별칭 — 없음 / 전부 / 고른 것만

      설치되는 스킬 이름(resume·wrap·svg-design)은 흔합니다. 내 PC에 같은 이름의 다른 스킬이 이미 있으면 그쪽이 이겨서, 설치는 됐는데 눌러 보면 엉뚱한 게 돌거나 쓰던 게 덮입니다. 이 질문이 그 회피 수단입니다 — 애칭 단디를 붙여 dandi-resume(앞) 또는 resume-dandi(뒤)로 만듭니다. 붙이기로 하면 붙일 글자(기본 dandi)와 위치(앞/뒤)를 이어서 묻고, 고른 것만이면 설치할 스킬 목록에서 직접 고릅니다. 기본은 없음이고, 설치 전에 같은 이름이 있는지 찾아본 뒤 있으면 그 스킬만 체크한 '고른 것만'을 권합니다. 기능 문서 세트 6종은 서로를 이름으로 부르니 여섯 개가 함께 움직입니다. 자세한 건 옵션 사전 2-7.

      이미 설치돼 있으면 — 유지 / 재구성 / 교체

      기존 설정이 감지된 항목마다, 모드와 상관없이 항상 물어봅니다. 눌러서 차이를 보세요.

      만들어지는 파일 미리보기

      챕터 7 · 문서 속 항목 ②

      개발 프로젝트용 — 02 분담 · 03 확장 · 04 검증

      코드를 다루는 프로젝트에서만 의미가 있는 세 문서입니다. 하나씩 펼쳐 보세요.

      02모델 분담 — 비싼 모델과 싼 모델을 나눠 쓰기 개발 전용

      어려운 분석·설계는 상위 모델, 잘 정의된 반복 작업은 하위 모델에 맡기는 서브에이전트 로스터를 깝니다. 아끼려고 어려운 일을 싼 모델에 밀면 "거의 맞는데 틀린" 결과가 나와 재작업이 더 비쌉니다 — 그래서 난이도 분류만큼은 상위 모델이 합니다.

      에이전트하는 일기본 모델
      surveyor구조를 넓고 기계적으로 훑어 목록으로 남김 (판단 안 함)sonnet
      triage훑은 결과에 난이도를 매김 — 가장 중요한 자리opus
      analyst어려운 부분을 분석해 구현 명세를 씀난이도별
      spec-writer새 기능의 요구를 확정해 명세를 씀 — 새로 만드는 일의 1단계opus
      implementer명세대로 구현 (범위 밖은 안 건드림)sonnet
      parity-tester테스트를 돌려 통과/차이만 보고haiku

      에이전트는 통째가 아니라 하나씩 고릅니다. 기존 코드를 고치는 일이면 spec-writer를 뺀 5종, 새로 만드는 일이면 surveyor·triage 없이 spec-writer부터 시작합니다. 리뷰어는 따로 안 만듭니다 — 내장 /code-review가 이미 있기 때문입니다.

      에이전트 파일에는 모델과 함께 추론 강도(effort)도 미리 적혀 있어서, 부를 때마다 고를 필요가 없습니다. 로스터를 팀과 공유할지(프로젝트에 커밋) 나만 쓸지(내 PC)도 함께 물어봅니다.

      여기에 선택 항목이 하나 더 있습니다(기본 해제) — 계획을 세울 때만 다른 모델로 돌리는 /plan-<모델> 명령. 계획이 끝나면 원래 모델로 저절로 돌아옵니다. 이 명령을 어디 둘지(나만 쓰는 내 PC / 팀과 공유하는 프로젝트)는 로스터와 따로 물어봅니다.

      ⚠️
      코드가 없는 저장소면 설치하지 않습니다 문서만 있는 곳에 로스터를 깔면 쓰지 않는 파일만 늘어납니다. Claude가 감지하고 알려줍니다.
      03확장 기능 — 상태 표시줄·디자인 스킬·MCP·브라우저·기능 문서·코드 리팩터링·한국 UI 기준 전부 선택
      • claude-hud — 입력창 아래 상태 표시줄. 컨텍스트·요금제 사용량이 보입니다. 절약 프로필이면 사실상 필수.
      • svg-design — SVG 시각효과(손그림·Gooey·유리·네온)를 제대로 구현하게 하는 규칙집. 웹 화면 프로젝트용.
      • frontend-design — Anthropic 공식 스킬. "AI가 만든 티가 나는 UI"를 피하게 합니다.
      • MCP 서버 — 외부 도구 연결(GitHub·문서 검색·브라우저 조작). 어떤 서버를 붙일지는 따로 물어봅니다.
      • 브라우저 검증 — 만든 화면을 Claude가 직접 열어 확인하고 고치게 합니다.
      • 기능 문서 스킬 세트(6종) — 코드와 실제 화면을 보고 기능마다 명세를 써 두고, 거기 적힌 테스트를 돌리고, 문서를 안 고친 커밋을 막고, 릴리스 노트까지 만듭니다. 6종을 한 세트로 깔며, 문서만 있는 저장소는 대상이 아닙니다. 팀원 전원의 커밋을 막는 커밋 가드는 기본으로 꺼 둔 채 따로 물어봅니다.
      • refactor — 코드를 정리하고(중복 통합·구조 정리·낡은 문법 제거) 동작이 그대로인지까지 증명합니다 — 호출처·계약·데이터 형식·실제 실행. 후보를 표로 보여주고 고른 것만 고칩니다. 문서만 있는 저장소는 대상이 아닙니다.
      • kr-ui-guide — 국내 서비스 리서치(UX 패턴·아이콘·색·최신 디자인 트렌드)와 한국 게임 UI/UX 리서치에서 추린 설계 기준. 제안하는 색의 명도 대비를 계산하고 화면을 체크리스트로 점검합니다. 한국 사용자 대상 웹·앱·게임 화면용이며, 특정 브랜드의 모양을 베끼지 않습니다.

      스킬을 고르면 두 가지를 더 물어봅니다 — 스코프(내 PC 전체 vs 이 프로젝트만)와 호출 방식(Claude가 알아서 vs 내가 /명령을 칠 때만). 기능 문서 세트·refactor·kr-ui-guide가 이미 dandi 플러그인으로 켜져 있으면 플러그인 유지(복사 안 함)와 복사본으로 교체 중 하나도 묻습니다 — 둘 다 두지는 않습니다.

      frontend-design이나 kr-ui-guide를 고르면 질문이 하나 더 붙습니다 — 폰트 라이선스 정책입니다. 설치한 스코프의 CLAUDE.md에 적힙니다. 자유 사용만(기본)은 자유롭게 쓸 수 없는 폰트를 거절하고 무료 대체 폰트를 제시하고, 안내 후 선택은 조건(구매·고지 의무·사용 범위)을 먼저 알린 뒤 내 결정을 기다립니다. 넣지 않음이면 정책을 적지 않습니다. 정책 한 곳이 어느 디자인 스킬에나 적용됩니다 — frontend-design은 혼자서는 라이선스를 보지 않으면서 타이포를 가장 적극적으로 바꿉니다.

      🔴
      회사라면 MCP는 대화 내용을 외부로 보낼 수 있고, 브라우저 연결은 로그인된 세션에 접근할 수 있습니다. 조직이 허용한 서버만 연결하고, 확장의 사이트 권한은 localhost로 최소화하세요.
      04검증 자동화 — "됐다"는 말 대신 기계 검사 훅 게이트가 핵심
      • 훅 품질 게이트 — Claude가 파일을 고칠 때마다 린터·문법 검사가 자동으로 돌고, 실패 출력이 Claude에게 돌아가 스스로 고칩니다. 절약 프로필이어도 빼지 않습니다 — 재작업이 줄어드는 게 가장 큰 절약이라서. 고르면 적용 범위(팀 공유 / 내 PC 전체 / 나만·이 프로젝트만)와 강도(실패하면 막기 / 경고만)를 함께 물어봅니다.
      • 호스트 CLI(gh/glab) — Claude가 PR을 만들고 CI 실패 로그를 직접 읽게 합니다. 로그인은 본인이 직접 합니다.
      • CI 통합 — PR에 @claude를 멘션하면 리뷰·수정. 🔴 회사면 조직 승인 필요 — CI에서 코드가 Anthropic API로 전송됩니다.

      훅에 느린 테스트는 넣지 않습니다 — 매번 몇 분씩 걸리면 세션이 답답해집니다. 그건 CI 몫입니다.

      챕터 8 · 문서 속 항목 ③

      05 출력 스타일 · 06 루틴

      05출력 스타일 — Claude의 말투·역할 바꾸기 선택

      내장 5종(Default·Proactive·Explanatory·Learning·Concise) 중 고르거나, 원하는 역할·톤을 마크다운 파일 하나로 직접 만듭니다. 배우는 중이라면 Explanatory(왜 그렇게 했는지 설명하며 진행)가 유용합니다.

      직접 만들 때는 스타일 파일을 어디 둘지(내 PC 전체 / 이 프로젝트)와 켜는 설정을 어디 쓸지(나만·이 프로젝트 / 내 PC 전체 / 팀 전원)를 따로 물어봅니다 — 파일을 PC 전체에 둬도, 켜는 설정이 이 프로젝트에만 있으면 다른 프로젝트에선 켜지지 않습니다.

      🔴
      커스텀 스타일의 함정 — keep-coding-instructions 기본값이 false인데, false면 Claude Code의 내장 코딩 지침이 통째로 사라집니다(검증 습관·최소 변경 원칙 포함). 코딩을 같이 할 거면 반드시 true로 두세요.

      또 하나 — 스타일을 바꾸면 다음 메시지부터 바로 적용됩니다(v2.1.251+). 스타일 파일을 고쳤을 때만 재시작이 필요합니다 — 파일은 시작할 때만 읽힙니다.

      06루틴 — PC를 꺼도 도는 클라우드 예약 작업 게이트 먼저

      Anthropic 클라우드에서 무인으로 도는 예약 작업입니다. 야간 PR 리뷰, 주간 문서 점검 같은 것. 설치 전에 반드시 아래를 묻습니다 — 코드로 확인할 수 없기 때문입니다.

      • ① 요금제가 Pro 이상인가 (+ claude.ai 계정에 GitHub 연결이 돼 있는가)
      • ② 회사 저장소라면 — 조직이 클라우드 실행(코드 반출)을 허용하는가
      • ③ GitHub 저장소인가 (현재 GitHub 전용 — 아니면 '해당 없음'으로 기록하고 다음에 다시 묻지 않습니다)
      • ④ 무인으로 돌려도 되는 일인가 — 루틴은 실행 중에 승인을 묻지 않으니, 배포·삭제·외부 발송처럼 되돌리기 어려운 일은 맡기지 않습니다
      💡
      내 PC의 파일이 필요하면 루틴이 아닙니다 루틴은 클라우드에서 돌아서 내 파일이 없습니다. "컴퓨터가 꺼져 있어도 돌아야 하는 것"에만 쓰세요.

      챕터 10 · 설치한 다음

      최신 상태로 유지하기

      한 번 깔면 끝이 아닙니다. 문서도 개정되고, 그 문서가 설치하는 스킬도 바뀝니다. 명령 셋이 서로 다른 세 질문을 맡는데, 이걸 헷갈리는 것이 낡은 구성을 계속 쓰게 되는 흔한 이유입니다.

      하고 싶은 것명령바뀌는 것
      뒤처진 게 있는지 알고 싶다/dropin-check없음 — 읽고 보고만 합니다
      문서 사본을 새것으로 바꾸고 싶다/dropin-update문서 파일만
      구성 자체를 최신으로 올리고 싶다/dropin-apply문서·설치된 스킬·설정

      사람들이 가장 많이 헷갈리는 것

      /dropin-update만으로는 업데이트가 아닙니다. 그건 설명서를 새것으로 바꾸는 일이지, 설명서가 만드는 물건을 바꾸는 일이 아닙니다. 설치된 스킬과 설정은 /dropin-apply를 돌리기 전까지 그대로입니다.

      아직 설치하지 않은 PC에서는

      /dropin-apply는 첫 설치 명령이기도 해서, 내가 어느 경우인지 따질 필요가 없습니다. 그 PC에 명령이 아직 없으면 말로 하면 됩니다: “저장소의 00_통합-설치.md를 받아서 이 PC에 적용해줘” — 그러면 이 명령도 다른 것들과 같이 깔립니다.

      이름만 보는 점검으로는 왜 부족한가

      스킬은 파일이 하나도 늘거나 줄지 않은 채 문장만 바뀔 수 있습니다. 파일 이름을 대조하는 점검은 그걸 “이미 최신”이라고 말합니다. 설치 절차는 파일 내용까지 대조하므로, 문장만 손본 개정도 내 디스크까지 도달합니다.
