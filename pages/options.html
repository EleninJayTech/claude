0. Eight words to know first

Know these and every choice below reads clearly

WordMeaning
Drop-in document “A manual you drop into a folder, say one sentence, and it applies itself.” The 00–06 files in this repository are exactly that. They are not a program but prose Claude reads and follows, so “installing” really means creating a handful of config files.
Scope How far a setting reaches. Global = every project on your machine (stored in ~/.claude/). Project = this one folder (stored in <project>/.claude/; commit it to git and your teammates get it too). When a choice says “pick a scope”, it is asking just you, or the team as well.
settings.json Claude Code’s config file. Mostly it records permissions — allow (run without asking), ask (prompt first), deny (forbid outright). Put .env under deny, for instance, and any attempt to read your password file is blocked.
Hook A rule saying “when this happens, run that command automatically.” These documents mostly use PostToolUse — it runs a linter or type check right after Claude edits a file. If it errors, the output goes back to Claude, which fixes it itself.
Skill / /command A single markdown file named SKILL.md becomes the /name slash command. Create skills/resume/SKILL.md and you can type /resume. The contents are simply instructions: “when this happens, do that.”
Subagent A helper Claude running in its own workspace, separate from the main conversation. Defined by .claude/agents/<name>.md, and each agent can use a different model. Hard analysis to the expensive model, repetitive work to the cheap one — that is the core of document 02.
MCP Model Context Protocol — the standard for plugging outside tools into Claude. Connect GitHub, a browser, or a document search and Claude uses them directly. Think of it as a USB port.
effort (reasoning depth) How hard the model thinks: low → medium → high → xhigh → max. Raising it improves hard design judgment but costs more tokens and more waiting. It is a separate axis from which model you pick.
💡 Why “saving tokens” keeps coming up Claude draws down your plan allowance in proportion to the characters (tokens) exchanged. So these documents share one principle: first, the best possible result; second, savings that do not cost quality. Verification, record-keeping and the stronger model on hard work are never cut in the name of thrift.

1. What order the questions come in

Inspect first → big choices → per-document details

Claude investigates before it asks. It checks the files for what is already installed, whether this is a git repository, which language the code is in, and then asks only about what the code cannot tell it. The result is far fewer questions than you would expect.

StepWhat happensWhat you choose
STEP 1Obtain the documents needed (01–06) — fetched from GitHub if not in the folderNothing
STEP 2Detect the environment — prior install record (dropin-applied), existing config files, project typeNothing
STEP 3The big choices — the five questions in §2 belowBase mode · bundles · profile · output language
STEP 4Install by each chosen document’s own procedure. Only in “custom” mode does it also ask about the per-document items (§3–§8)Depends on the mode
STEP 5Verify, report, and leave one install-record line at the bottom of CLAUDE.mdApproving the commit
📌 Outside “custom” mode the detailed questions are skipped Choose minimal, recommended or full and the per-document items are settled automatically at that mode’s defaults. So §3–§8 below are what you read either when you want to choose yourself, or when you want to know what gets switched on for you. The safety questions (overwrite what is already here? have you checked company policy?) are never skipped, in any mode.

2. The five opening questions

Answer these and the install runs itself

2-1. Target — this PC, or this project

Asked only when it is ambiguous. Choose PC and settings land in ~/.claude/ (your account folder); choose project and they land in this folder’s .claude/. Most people do the PC setup once, then go project by project.

2-2. Base mode — one of four (single choice)

Minimal01 only

Only the record system and security. Even within the document, only the essentials.

What appears
A global settings.json (security locks), the /resume, /wrap and audit skills (/dropin-check, /dropin-update), and three docs/ files in the project
Choose it when
The repository is documentation with no code, or you just want the basics first
Recommendeddefaultauto-combined per situation

Claude combines things based on what it detected and shows you in one line why it chose that.

The rule
New PC → 01 (global) + 03 (HUD) / development project → 01+02+04 / documentation or non-code repository → 01 only / somewhere 01 already exists → only what is still missing and needed
Choose it when
Most of the time. If you are unsure, this is the answer
Fullall of 01–06

Anything that does not apply (02 in a repository with no code, say) is dropped and reported.

Note
Even “full” never overwrites existing settings silently — it asks keep / reconcile / replace every time
Choose it when
You want a new project set up properly and have time to answer questions
Customtwo-stage manual choice

Pick the documents, then pick the items inside them. Everything in §3–§8 below arrives as a question.

Choose it when
You want exactly what you need and nothing else — typically after one install has taught you the structure

2-3. Purpose bundles — zero or more (multi-select)

Bundles are unioned onto the base mode. Pick “recommended” + “design” and the design extensions are added to whatever recommended selected.

2-4. Operating profile — standard / thrift

Standarddefault

Quality first. Leaves effort at its default and uses the stronger model for hard work.

ThriftPro plan · managing an allowance

For when the usage allowance matters. What it cuts is only defaults and waste.

What changes
Sessions start at /effort medium · subagents are assigned mostly to Sonnet · a smaller roster · claude-hud pre-checked (you cannot economize on what you cannot see)
What is never cut
Difficulty triage · final review · verification gates. Saving here costs more in rework

2-5. Output language — Korean / English

This is the language of what gets generated, not the language of the documents. The drop-in documents (00–06) are written in Korean and there is no translation, because Claude executes them identically either way. This question decides the language of what the install produces.

Languagedefault = the language you are chatting in

Your answer sets the language of the target CLAUDE.md body, the docs/ record entries, commit messages and generated filenames.

Filenames change too
docs/난이도-매트릭스.md ↔ docs/difficulty-matrix.md, docs/핸드오프-규약.md ↔ docs/handoff-protocol.md. If one already exists under another name, that name is kept
What does not change
Format keywords — markers like [topic][Done] and dropin-applied are fixed regardless of language, because /resume, /wrap and the check script find them by those exact strings
If records already exist
Their language wins — mixing languages inside one file splits the record that /resume reads
Where it is stored
As 언어=ko or 언어=en in the install record, so it survives re-application

2-6. If something is already installed — keep / reconcile / replace

Asked separately for each item where existing settings were detected. Asked always, whatever the mode.

  • Keep — skipped, untouched. This one if it is working for you.
  • Reconcile — only the parts that drifted are aligned. For keeping what you have while taking in the newer version.
  • Replace — the old one is removed and rebuilt. For cleaning up something you threw together earlier.

3. 01 Base setup — records and security

Six items ⓐ–ⓕ (multi-select · all pre-checked)

What this document does is abolish “what was I doing yesterday?” It has your work recorded to files so the next session picks up with a single /resume. Secret protection is layered on top.

ⓐGlobal behavior rulespre-checked

Applies working habits for Claude — “ask instead of guessing”, “build nothing beyond what was asked” — across your whole machine.

File created
~/.claude/CLAUDE.md
Example contents
State assumptions · simplicity first · don’t touch code outside scope · no re-printing whole files · never read .env
Can I skip it
If you already run your own global rules, answer “keep”
ⓑGlobal securityunchecking not advised

Blocks Claude from reading password and certificate files, and warns you when the conversation is about to be compacted.

File created
permissions.deny and hooks in ~/.claude/settings.json
What it blocks
Reading .env, *.pem, *.key — and the shell-command detour such as cat .env along with it
Limits
It cannot stop a Python or Node script from opening the file itself. The real fix is keeping secrets out of the repository
If you skip it
Claude may read a password by accident and it stays in the transcript. Leave it on unless you are skipping it deliberately
ⓒ/resume · /wrap · audit skillspre-checked

Two slash commands for opening and closing a session, plus two for auditing your setup. This is the practical heart of the whole thing.

Files created
skills/resume/SKILL.md · skills/wrap/SKILL.md · skills/dropin-check/ · skills/dropin-update/
/resume
Pulls from the remote first if there is one, finds uncommitted changes (work in progress), reads the last records, plan and recent decisions, and reports “last time X, next is Y?”. If the install is old (30+ days) it suggests an audit
/wrap
Appends today’s work to the record, files new decisions, updates the plan checkboxes, and warns you if nothing is committed
/dropin-check
Audits only whether your setup matches the documents’ current version (changes nothing)
/dropin-update
If the document copies in your project are stale, asks first and then replaces them with the current ones
Variants
resume and wrap come in three shapes depending on your environment — the basic single-repository form, a split form for a team sharing one repository, and a unified form for several repositories under one folder
ⓓProject record systempre-checked

Decides where and in what format records are kept, and pins those rules into the project’s CLAUDE.md.

Files created
docs/PROJECT_PLAN.md (roadmap) · docs/PROGRESS.md (session log) · docs/DECISIONS.md (decision log) · .gitattributes · .gitignore
The core rule
Records are appended at the top only; past lines are never edited. When your thinking changes you add a new decision and mark the old one “superseded”
.gitattributes
merge=union — when two people append at once, both entries survive with no git conflict
.gitignore
Keeps personal settings (.claude/settings.local.json) and isolated work folders (.claude/worktrees/) out of commits — without it, the contents of an isolated checkout all show up as untracked
ⓔProject permissionspre-checked

Decides what may run without asking in this project.

File created
.claude/settings.json
allow examples
git status, git diff, npm run, ./gradlew — safe and frequent
ask examples
git push --force, git reset --hard, rm -rf — hard to undo
Note
Allowing everything with Bash(*) is a personal choice and is not recommended for teams
ⓕeffort & cache guidanceadvice only · no file

You are told when to raise and lower reasoning depth, and which habits keep the conversation cache intact. No config file is written.

Why no file
Pinning effortLevel in the project settings silently overrides whatever you chose with /effort, with no warning. Better to leave the default and change it with /effort when you need to
Why the cache is money
Every turn resends the whole conversation, but when the front of it matches the previous turn it is read from cache at roughly 10% of the price. Change one thing and everything after it is reprocessed — the second axis of thrift is not “use less” but “avoid being reprocessed”
Avoid mid-task
/model switches, /effort changes, turning on fast mode, /compact — all of these break the cache. When you need them, batch them at the start of a session
Free to do
Entering and leaving plan mode, calling skills and commands, /rewind, editing files, switching permission modes — the cache survives
/clear over /compact
/clear sends no request, so it costs nothing, while /compact is itself a large request that builds a summary. Do it after /wrap though — /clear has no safety gate, so unrecorded decisions vanish with it
Measuring
The Prompt cache line in /usage. Misses piling up every turn mean one of the breaking actions above is happening mid-task

Confirmed alongside — the project type

Determined from the files, then merely confirmed with you: “here is how I read it”.

TypeThe situation
B (single)One git repository. The most common case
A-1 (unified)Several repositories side by side under one parent folder — start Claude in the parent and it sees them all
A-2 (unified)Several repositories scattered around — needs the --add-dir option
Mixedgit repositories and plain folders (no git) mixed under one parent — each folder gets the treatment that fits it
Non-git folderA folder with no git at all — git is suggested, and if you decline, only the record system is installed
+ MSA splitOn top of the above, several people editing the same part of one repository at once → the record folders are split per unit (not per build module, but per unit people actually divide). Unnecessary if you work alone

For a bundle of repositories (A-1, A-2, mixed) two things are confirmed per repository: ① company or personal (a personal folder can hold company repositories, so this is never asked once for all) and ② whether to install into the sub-repositories too (installing from the parent still leaves the choice per repository). Teammates installing from different places (parent folder vs. individual repository) do not collide.

4. 02 Model split — the subagent roster

ⓐ–ⓔ plus per-agent selection · development projects only

A setup that splits expensive and cheap models by how hard the work is. Hard analysis and design go to the stronger model; well-defined repetitive work goes to the cheaper one. Push hard work onto a cheap model to save money and you get results that are almost right but wrong, and the rework costs more — which is why the triage itself always uses the stronger model.

⚠️ Not installed in a repository with no code Installing a roster in a documentation-only repository just adds files nobody uses. If the scan finds no build and no code, Claude says so and stops.

Items ⓐ–ⓔ

ⓐDifficulty rubricpre-checked

The reference table for what counts as hard in this project. Without it there is nothing to route on.

File created
docs/difficulty-matrix.md (docs/난이도-매트릭스.md when the output language is Korean)
Hard
Cryptography, authentication, concurrency, state management, external integration contracts, huge tangled files, performance-critical paths
Easy
Plain CRUD, lookups, fixed-format conversions, boilerplate
ⓑThe roster — chosen agent by agent

Not as a block but one at a time. Only those matching the work you are doing are pre-checked.

AgentWhat it doesDefault model
surveyorSweeps the structure broadly and mechanically into lists and tables. Makes no judgmentssonnet
triageScores the sweep against the rubric. The highest-leverage seatopus
analystAnalyzes hard modules in depth and writes the implementation spec (success criteria, samples, risks)by difficulty
spec-writerPins down requirements for new features and writes the spec — a wrong spec means everything downstream is rework, hence the expensive modelopus
implementerBuilds from the spec. Touches nothing outside scopesonnet
parity-testerRuns the tests and reports pass/diff only, fast. Root-cause analysis goes back upstreamhaiku
How to choose
Changing existing code (migration, refactor) → the five without spec-writer. Building something new → drop surveyor and triage and start from spec-writer
Where they live
Shared with the team = the project’s .claude/agents/ (committed, everyone uses them) / personal experiment = ~/.claude/agents/ (your machine only). Asked in every mode
Parallel option
When the job is large and the slices never touch the same files, running several implementers at once (isolation: worktree) is offered as a choice
ⓒCustom reviewerunchecked by default

An agent for code review. Not created by default — Claude Code already ships /code-review.

Check it when
You have project-specific criteria the built-in review cannot know — cross-checking spec against implementation, enforcing domain conventions
Note
The built-ins are /code-review (general) and /simplify (simplification only — it does not hunt bugs)
ⓓHandoff document protocolpre-checked

The rule that results pass between stages as files. Handing them over as a chat summary leaks content and fails.

File created
docs/handoff-protocol.md (docs/핸드오프-규약.md in Korean; if a protocol already exists under another name, that name is kept) — which stage leaves what in which file
ⓔPlanning-only model commandunchecked by default

Creates one /plan-<model> command that runs a different model only while planning. When the plan is done it returns to your normal model by itself — nothing to undo.

Why build it yourself
The only combination Claude Code ships is opusplan (plan = Opus, execute = Sonnet). Any other pairing — planning with Fable, say — only exists if you make it
File created
One skills/plan-<model>/SKILL.md. Whether it stays on your machine or is shared with the team is asked together with ⓑ
Check it when
You want a specific model just for the planning stage. Most projects do not, so it is unchecked by default

6. 04 Verification — a three-item checklist

Machinery that stops “I verified it” from being just words

Document 01 already carries the rule that actual command output, not the sentence “I ran the tests”, is what counts as evidence. But rules get forgotten, by people and by AI alike. So 04 mechanizes it with two gates — on every file edit (hooks), and before merging (CI).

§1Hook quality gatehighest impact

A linter or syntax check runs automatically every time Claude edits a file. On failure the output goes back to Claude, which fixes it itself.

File changed
hooks.PostToolUse in .claude/settings.json
Example commands
Flutter → flutter analyze · JS → node --check · TS → npm run check-types
What not to put here
Slow tests. Minutes on every edit makes the session sluggish and burns tokens — that is CI’s job
Even on the thrift profile
This is never dropped. Less rework is the biggest saving there is
Scope
Shared with the team = project (committed → applies to everyone, so get approval for a company repository) / you, every project = global / you, this repo only = .claude/settings.local.json (not committed — use this when the command is stack-specific and would break elsewhere)
Strictness
Blocking (stop on failure and fix immediately) / warn only (report and continue) — asked together with the scope
§2Host CLI (gh / glab)optional

The command-line tool that lets Claude open PRs, read issues, and read CI failure logs directly so it can fix them.

Which one
GitHub → gh / GitLab (including self-hosted) → glab / any other host → not installed
Install
Windows: winget install GitHub.cli; macOS: brew install gh → then gh auth login
Authentication
You sign in yourself, in a browser. Claude never creates or stores a token
§3CI integration🔴 org approval required at work

Claude joins the review at the PR stage. Mention @claude on a PR and it reviews or fixes.

GitHub
Creates .github/workflows/claude.yml — the official action anthropics/claude-code-action@v1
GitLab and others
GitLab uses the canonical template from the official CI/CD integration (beta); other hosts fall back to calling claude -p "…" directly in a CI step
Requires
ANTHROPIC_API_KEY in the repository secrets (Pro/Max subscribers can use CLAUDE_CODE_OAUTH_TOKEN instead); GitLab needs an access token too. Claude cannot add these for you — you register them yourself
At work 🔴
CI sends your code to the Anthropic API. Check your organization’s external-AI policy first. Without approval, it is not installed

7. 05 Output style — changing tone and format

Two items (multi-select)

💡 How this differs from CLAUDE.md CLAUDE.md holds facts and rules — “this project uses Flutter and the tests run with this command”. An output style changes Claude’s role itself by modifying the system prompt, so it lives at a different layer. Do not write the same thing in both.
§1Switch a built-in styleno file created

You simply pick one of the five that already exist.

StyleCharacter
DefaultThe baseline, tuned for software work
ProactiveMore autonomous — infers and acts without asking about most things (your permission settings still hold)
ExplanatoryWorks while explaining why it implemented things that way. Useful while you are learning
LearningAdds TODO(human) markers so you write some of the code yourself
ConciseLeads with the result and drops preamble and narration — the thoroughness of the work is unchanged
How to switch
Output style in the /config menu. The old /output-style command has been removed
⚠️ Gotcha
It does not affect the current session — the system prompt is read once, at session start. After switching, run /clear or open a new session
§2Create a custom styleoptional

Write the role, tone and format you want into a single markdown file.

File created
output-styles/<name>.md
Follow-up questions
Purpose (which role and tone) · scope (global or project) · whether to keep the coding instructions · where to switch it on (which settings file gets the activation key — a separate axis from where the file lives: the default picker saves only to this repo’s personal settings, so a globally-created style still will not activate in other projects) · and if you also chose a built-in switch, which one is active now
🔴 Gotcha
keep-coding-instructions defaults to false, and false makes Claude Code’s entire built-in coding guidance disappear — verification habits and the minimal-change principle included. If you will also be coding, set it to true. Use false only for a genuinely different role, such as writer or analyst
Cost
The style body is a fixed cost loaded into the system prompt every session. Keep it to a few dozen lines
Where it does not apply
Not to subagents — each of those uses its own prompt

8. 06 Routines — jobs that run while your PC is off

Three items once the gate is passed · research preview

A routine is a scheduled job that runs unattended in the Anthropic cloud. Even with your machine off, it clones the repository at the appointed time, does the work, and leaves the result as a PR or a comment — nightly PR review, weekly doc checks, that sort of thing.

🔴 §1 Preconditions — fail these and nothing is installed ① Is your plan Pro or above, with access to Claude Code on the web?
② For a company repository — does your organization permit cloud execution (code leaving the building)? A routine clones the entire repository to the cloud and the prompt is stored there too
③ Is it a GitHub repository? (GitHub only, for now)
④ Is GitHub connected to your claude.ai account? If not, you build the whole prompt and schedule and the final save is rejected (observed in practice)
None of these can be checked from the code, so they are always asked.
§2Repository prerequisitesoptional

Groundwork so the job actually works in the cloud.

The key point
A routine cannot use the personal MCP servers registered on your machine. If it needs them, commit them to the repository as .mcp.json
What comes along
CLAUDE.md and .claude/settings.json are in the clone, so they apply unchanged — document 01’s record rules stay alive in cloud runs too
§3Creating a routine — pick one of three triggers
TriggerHow to create itExample use
Schedule/schedule <plain English> — minimum interval one hour; one-off runs allowedWeekly doc checks, backlog grooming
APICreate it on the web, then call it with a dedicated tokenMonitoring alert → investigate cause → draft PR
GitHubCreate on the web or with /schedule — events such as PR opened or merged, plus filtersChecklist review when a PR opens
Decided alongside
Target repository · the prompt · the connectors it needs (everything is included by default, so remove what you do not need — least privilege)
On the thrift profile
You are advised to start weekly. Routine runs consume your plan allowance too
§4Definition record: docs/ROUTINES.mdrecommended

A routine’s configuration lives only in your claude.ai account, never in the repository. Move accounts, or have a teammate recreate it, and there is nothing to reproduce it from. So each one gets written down in the repository.

💡 When a routine is the wrong tool If it needs files or tools on your own machine, it is not a routine — it runs in the cloud, where your files do not exist. Use the desktop app’s scheduled tasks, or /loop inside a session, instead. Routines are for “must run with the computer off” and “react to GitHub events” only.

9. If this is your first time, pick these

Recommended combinations by situation

SituationMode · bundles · profileWhy

10. Commonly confused

Can I run it again if it is already installed?

Yes — that is the intended use. When an install finishes, a line like this is left at the bottom of CLAUDE.md:

Run it again later and Claude reads that line first, then summarizes what changed in the documents since. Even at the same version it asks “shall I audit the existing items? add what you skipped last time?”, and if something was left pending last time (“awaiting gh authentication”, say) it checks whether that is now resolved. If it is resolved but you still do not want it, that is recorded as “not selected” — so the same question stops coming back.

If I skip a checkbox, is it gone for good?

You can run it again any time and add it. The documents are independent, so order barely matters — though 02 flows naturally once 01’s record system is in place.

I am worried something will get overwritten

The principle running through the whole install is “never overwrite without approval”. Detected settings always prompt keep / reconcile / replace, and edits to settings.json merge just that key rather than replacing the file. Secrets (.env, keys, certificates) are neither read nor committed.

I installed it but /resume does not appear in autocomplete

Restart the IDE or terminal. If that does not do it, checking the folder and file name (skills/resume/SKILL.md) and the name: line at the top of the file solves it in nearly every case.

Typing /resume shows several entries with the same name — did it install wrong?

Usually that is correct. The setup puts a copy in the repo (.claude/skills/) to share with the team and another on your machine (~/.claude/skills/) to actually run, so one machine holds two copies of the same name and autocomplete lists them separately. Whichever you pick, the one on your machine runs (the official precedence). What matters is not the count but whether the two copies have the same content — if they differ, tell Claude to “align the global skill with the repo copy”. The exception: two entries caused by a leftover ~/.claude/commands/resume.md from the old style — delete that file.

The “document version” keeps climbing — must I keep up every time?

No. Most version bumps are simply a re-check against the official documentation, recording that it still holds. Changes that actually alter what gets installed are bold in the version table, so judging from the summary Claude shows you on re-application is enough.
