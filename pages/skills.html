Fifteen skills, one slash away —
here is what each one actually does.

A skill is a folder of instructions Claude loads on demand. Dandi installs fifteen of them. This page is the field guide: what each does, when to reach for it, what it leaves on disk, and the places it bites.

← Back to the guide · 1-minute intro · Install walkthrough · Options dictionary · Course · GitHub repository ↗

First, what is a skill?

If you have never used one: a skill is not a plugin you launch and not a library you import. It is a folder with a SKILL.md inside, and Claude reads it only when it is needed — so having fifteen installed costs you nothing until you call one.

01 A folder with a SKILL.md

The front matter carries the name and a description; the body is the procedure Claude follows. Some skills ship extra files under references/ or scripts/ — those are part of the skill, not optional extras.

02 Two ways to run

Type /name to call it yourself, or let Claude match the description to what you asked and load it on its own. Skills that touch your browser or your source code are set to manual-only on purpose.

03 Two places to live

~/.claude/skills/ is yours on this machine; .claude/skills/ inside a repo is shared with the team through git. If the same name exists in both, the personal one wins — the project copy simply never runs.

One more thing before the list: during install you may have given the skills a name prefix or suffix (an alias, like feature-docs-dandi). If you did, read every /command below with your alias applied.

Running a session

installed by document 01 §D-4 · global scope

These four are the heartbeat of the setup. Two of them open and close every session; the other two tell you whether your configuration has drifted behind the documents it came from.

/resume
no arguments

Opens the session by reconstructing where you left off — from git and from your own records, not from memory.

Use when
At the very start of a session, and again after /clear.
It does
Pulls with --ff-only if the tree is clean, finds uncommitted work through git status, then reads the top of PROGRESS.md, the last three decisions, and PROJECT_PLAN.md.
You get
A short "last time you did X, next is Y?" report, plus reminders when a scheduled check has come due.
Worth knowing. It reads only the ~5 newest entries, capped at ~700 characters each. Anything the next session must pick up belongs at the front of an entry — text at the end falls outside the cap and is never read.
globalread-mostly
/wrap
no arguments

Closes the session by writing today into the record, so the next /resume has something to find.

Use when
Before you stop working — and always before /clear.
It does
Appends an entry to PROGRESS.md, adds any new decision as DEC-YYYYMMDD-<author>, ticks the boxes in PROJECT_PLAN.md, and warns you if changes are still uncommitted.
You get
One line per session, in the fixed shape [topic][Done] … — @author (branch) date.
Worth knowing. Records are append-only. When a decision changes you add a new one and mark the old "Superseded by" — you never edit history in place.
globalwrites records
/dropin-check
no arguments · read-only

Tells you whether the configuration on this machine has fallen behind the documents that produced it.

Use when
/resume says the install record is over 30 days old, or you simply want to know if anything drifted.
It does
Compares the project's dropin-applied record and your global ~/.claude against the current versions in the document repository, and reports differences only.
You get
A difference report. Nothing is installed, nothing is edited.
globalno writes
/dropin-update
no arguments

Brings your copies of the drop-in documents up to date — the documents themselves, not the configuration they describe.

Use when
/dropin-check reported that your document copies are older than the published ones.
It does
Works out how the documents got here — copied into the project, referenced from a local clone, or read straight from raw URLs — and updates each in the way that fits, after asking.
You get
Refreshed document files. Re-applying the configuration is a separate step, driven by document 00.
Worth knowing. It refuses to run inside the source repository itself — there, git pull is the update path.
globalasks first

Feature docs, tests, releases

installed by document 03 §7 · a set of six

These six are one machine with six levers. They share the same file names and front-matter keys under docs/features/, so they are installed together or not at all — a partial install fails quietly rather than loudly. /feature-docs init is the door; the other five refuse to start until it has run.

/feature-docs init → docs/features/ → 00_inventory · 03_test_index · F-001…
/feature-testruns the cases on the real screen
/test-to-scriptturns cases into Playwright · Maestro
/feature-doc-auditfinds docs that fell behind
/feature-doc-guardblocks commits that skip the doc
/release-notesgroups the history by feature
/feature-docs syncfolds the changes back in

The order to switch them on

The fan above shows what connects to what, not what to do first. Adopting them in this order means each step is useful on the day you take it — and the two that constrain you arrive after the thing they constrain is worth trusting.

1
/feature-docs init
The door, and the only step with no alternative — four of the other five stop with “run init first” until docs/features/ exists. It reads the whole codebase, so give it a quiet slot rather than squeezing it in before a release.
2
/feature-test
Before you trust the spec, watch it run. Step 1 wrote down what the code appears to do; this is the first thing that checks whether that is actually true. A spec that is wrong is much cheaper to fix here than after step 3 starts enforcing it.
3
/feature-doc-guard install
Lock it only once it is worth locking. Install the commit guard over a spec you have not verified and every commit is now blocked by a document you do not believe — the usual outcome is that someone disables the guard, permanently.
4
/feature-docs sync
From here it is a loop, not a step. Run it after each change; the guard from step 3 is what reminds you when you forget. This is the one you will use hundreds of times — the other five are occasional.
5
/test-to-script
After a case has been run by hand enough times to annoy you. It converts that case into Playwright or Maestro, and /feature-test then prefers the script automatically. Doing this on day one means automating cases you do not yet know are worth keeping.
6
/feature-doc-audit
Periodic rather than reactive — it needs elapsed time before it has anything to find. Light enough to schedule: claude -p "/feature-doc-audit" on a weekly timer is the usual arrangement.
7
/release-notes
Release day. It is the one skill here that does not stop without init — with no feature docs it falls back to reading git log alone. It still works; it just produces a list of commits instead of a list of features.

Steps 1–3 are a one-time setup; 4 is the everyday habit. If you only ever adopt part of the set, adopt that prefix — steps 5–7 each pay off later, and none of them is a prerequisite for the others. What you should not do is skip step 2 to reach step 3 faster.

/feature-docs
init | sync [base commit or tag]

Writes down what the program actually does, checked twice: once in the code, once on the running screen.

Use when
init for a project with no spec yet (it works incrementally, so a big codebase is fine); sync after you add or change a feature.
It does
Detects the stack, walks the features, drives the real UI through Chrome MCP or an emulator, and records every claim with the commit, branch and app version it was observed at.
You get
docs/features/ — an inventory, a screen-flow map, a data model, a test index, one file per feature, and screenshots.
Worth knowing. It never guesses. Code-only evidence is labelled as such, and destructive actions (delete, payment, send) are documented from the code and marked unverified rather than executed.
entry pointwrites docsdrives the UI
/feature-test
[F-003 | TC-F003-01] — all if omitted

Runs the test cases from the spec on the real screen and, when one fails, works out whose fault it is.

Use when
You want to know whether features still work — before a release, or after a risky change.
It does
Follows each case exactly as written, prefers a converted script when one is registered, and files every failure as (A) code bug, (B) stale doc, (C) environment, or (D) not enough evidence.
You get
A dated report under docs/features/test_reports/ with screenshots, and a summary in the chat that separates newly failing from newly passing.
Worth knowing. It fixes nothing — not the docs, not the code. Even a confirmed stale doc is repaired afterwards by /feature-docs sync, with your approval. It is set to manual-only, because it operates your browser.
manual onlyneeds initdrives the UI
/feature-doc-audit
[commits-behind threshold, default 5]

A cheap health check on the docs — no browser, no tests, just arithmetic against git.

Use when
Weekly, or whenever you want to know which feature to sync first without paying for a full test run.
It does
Finds docs lagging behind HEAD, leftover unverified items, inventory mismatches, code references pointing at files that no longer exist, and cases missing from the test index.
You get
A table and a suggested sync order. Light enough to schedule: claude -p "/feature-doc-audit".
The trap. Needs Python 3. Check it with python -c "print(1)", not python --version — a Windows app-execution stub answers the version call and exits 0 while doing nothing at all.
needs initneeds Python 3no writes
/feature-doc-guard
install | uninstall | check

Stops the commit where the code moved and the doc did not.

Use when
Once the spec exists and you want it to stay true without anyone having to remember.
It does
Installs two guards — a .git/hooks/pre-commit hook and a Claude Code PreToolUse hook — that trace each staged source file back to the feature that owns it and block the commit if that feature's doc is not staged too.
You get
A blocked commit with the list of missing docs. Unmapped files only produce a warning, never a block. Emergency bypass: FEATURE_DOC_GUARD=0.
Remove it in order. Run /feature-doc-guard uninstall before deleting the skill folder. Delete the folder first and the pre-commit hook stays behind, blocking commits with no visible way to lift it.
needs initneeds Python 3installs hooks
/test-to-script
[F-003 | TC-F003-01] — all unconverted if omitted

Turns the hand-run cases into scripts a machine can run at three in the morning.

Use when
You want tests in CI or on a scheduler. Unattended runs need this — Chrome MCP wants a real browser and fails quietly without one.
It does
Converts cases to Playwright (web) or Maestro (Android, iOS), proposes data-testid attributes where the selectors are fragile, and registers the mapping in 04_script_map.md.
You get
Runnable test files, plus /feature-test automatically preferring the script for every case it registered.
Worth knowing. Manual-only by default, because stabilising selectors means editing your source.
manual onlyneeds initedits source
/release-notes
[from tag] [to tag — HEAD if omitted]

Writes release notes a user can read, built from the feature docs rather than from the commit log.

Use when
You are cutting a release and need to say what changed in it.
It does
Collects the change history in each feature doc, the version history, the git log and the latest test report, then groups everything by feature — several commits on one feature become one line.
You get
docs/releases/<tag>.md, split into new, changed, fixed, removed, internal, and tests — with a separate list of commits no doc covers yet.
Worth knowing. It refuses to invent. When a commit message is unclear it reads the diff, and if that still does not settle it the line is marked for you to confirm.
needs initwrites docs

Code quality

installed by document 03 §8 · stands alone

Independent of the six above. It will use the feature docs if they happen to be there, and works perfectly well when they are not.

/refactor
[all | path | commitA..commitB | check [scope]] [nocheck]

Improves the code without changing what it does — and then proves it did not change what it does.

Use when
Duplication has piled up, a structure needs untangling, a runtime version moved, or something is slow. Never for a new feature or a bug fix — keeping those out of the same change is the whole premise.
It does
Picks a scope (uncommitted work by default), shows you a table of candidates and waits for your approval, refactors, then verifies across baselines, call-site contracts, characterization tests, static checks and real runs.
You get
A report in the chat, saved to docs/refactor/ on request. It never commits — you do, ideally one change per commit.
When to run
Right after a feature works and before you commit it, as its own change. Not while you are still adding to it — a refactor mixed into a feature commit is one nobody can review or revert separately. Not on code you have no way to exercise either: the verification stage is most of this skill's value, and without a test or a runnable path it has nothing to compare against. On a scope you are unsure about, run /refactor check first — it verifies without touching a line.
Read the front matter correctly. allowed-tools widens what runs without a prompt; it is not a sandbox. This skill can edit files despite the git-only list. The key that restricts is disallowed-tools.
edits sourceapproval gatecheck = verify only

Planning with another model

installed by document 02 STEP 3 ⓔ · off by default

Separate from everything above. It plans; it does not implement. The name ends in the model you picked at install time — /plan-fable, /plan-opus and so on.

/plan-<model>
what to plan · manual call only

Plans a change with a stronger model than your session uses, writes it down, and stops before any code.

Use when
A change could go several ways and you want the judgement made before anyone starts typing. Not for a routine change with one obvious path.
It does
Enters plan mode, reads only what it needs, and writes a plan that a cheaper model can follow without exploring again: what is confirmed, small steps, a check for each step, and the reason behind each decision.
You get
A plan file copied to docs/plans/. The turn ends there — you start the implementation with a new prompt, on your usual model.
Worth knowing. That one turn runs on the other model, and caches are per model, so the conversation so far is re-read once without cache. Call it early in a session or right after /clear.
global or projectoff by defaultno code changes

Front-end design

installed by document 03 §2, §3 and §9 · optional

Three skills that only matter if you build UI. None of them writes records or installs hooks — they shape how Claude designs and writes front-end code when you ask for it.

/svg-design
no arguments — describe the effect you want

Builds SVG filter effects — hand-drawn wobble, gooey blobs, liquid glass, neon text — that survive contact with real browsers.

Use when
You are writing inline SVG filters, wrapping one in a React or Next.js component, or an effect looks right in Chrome and wrong in Safari.
It does
Carries the rules that are easy to get wrong: unique filter ids from useId() so hydration does not break, padding around blur so WebKit stops clipping, and octave limits so phones keep their frame rate.
You get
Filter code that is accessible and does not thrash the GPU cache on every render.
globalfront-end only
/frontend-design
no arguments — describe the UI

Pushes a new interface away from the default look that every AI-generated page shares.

Use when
Starting a new screen, or reshaping one that came out looking templated.
It does
Asks for a deliberate point of view on palette, typography and layout, grounded in the subject rather than in a component library's defaults.
You get
Design direction before the markup, which is the only point where it is cheap to change.
Worth knowing. This one is published by Anthropic and installed with npx skills add -g, so it updates on its own schedule rather than with the Dandi documents.
globalfront-end only
/kr-ui-guide
no arguments — it loads itself for UI, icon and colour work

Holds a screen for Korean users to the rules Korean services converged on — and does the contrast maths instead of eyeballing it.

Use when
Designing a flow, choosing or drawing icons, or settling a palette, dark mode or design tokens for a Korean-audience product.
It does
Loads only the summary for the kind of work at hand, applies seven hard rules (contrast, bright colours as surfaces only, state by shape as well as colour, 44pt/48dp targets, labelled icons, one accent action, no dark patterns), and cites the principle or checklist item behind each proposal.
You get
A design proposal with its reasoning, a self-check against the checklist, and every colour pair given with a calculated contrast ratio.
Worth knowing. The case studies name real brands. The skill takes the principle, never the brand’s colour or icon, and treats the reports’ conversion figures as unverified.
globalKorean audience

A day, in the order the skills come up

You will not use fifteen skills in a day. A realistic week looks closer to this.

/resume

Opens the session. Pull, uncommitted work, the last few entries, what is due. Roughly thirty seconds before you have your bearings.

— you build the thing —

Ordinary work. No skill required.

/refactor

Once the feature works, tidy it as a separate change. The approval gate means you see the candidate list before anything moves.

/feature-docs sync

Folds what you changed into the spec. If /feature-doc-guard is installed, the commit will not go through until you do.

/feature-test F-003

Runs just the affected feature's cases on the real screen. Full runs are for release day.

/wrap

Writes today into the record and warns about anything uncommitted. Always before /clear.

/release-notes v1.0.0

Release day only. Reads the feature docs the rest of the week built up.

Six things that surprise people

The personal copy wins, silently.

Same skill name in ~/.claude/skills/ and in the project's .claude/skills/? The personal one runs and the project one never does — with no error to tell you. This is the most common reason a team's shared skill "does not work" on one machine.

allowed-tools is a permission, not a fence.

It widens what may run without prompting. A skill listing only git commands can still edit your files. The key that actually restricts is disallowed-tools.

The six feature skills are one unit.

They call each other by name and share file names under docs/features/. Install a subset and the rest fail quietly. If you use an alias, apply it to all six — or to none.

A Python that is not there can still answer.

On Windows, the app-execution stub prints Python with no number and exits 0. Two skills depend on real Python; verify with python -c "print(1)" and look for the 1.

Uninstall the guard before deleting its skill.

The instructions for removing the commit guard live inside the skill. Delete the folder first and only the hook remains — commits keep failing and the cause is nowhere on screen.

An alias is two edits, not one.

Renaming the folder is half of it; the name: in the front matter has to match. If they differ the skill never loads, and nothing says why.
