이 세션의 범위는 **`$ARGUMENTS`** 까지다. 세션이 끝날 때까지(`/clear` 전까지) 아래 규칙을 따른다.

`$ARGUMENTS`가 비어 있으면 무엇까지 할지 한 줄로 묻고 멈춘다.
다시 선언하면 새 선언이 앞 선언을 대체한다. 아래 고정 문구(`세션 범위:` 등)는 사용자와 대화하는 언어로 옮겨 쓴다.

## 선언 직후

범위를 한 줄로 되풀이한다 — `세션 범위: <작업>`. 그다음 요청받은 작업을 이어서 진행한다(이미 진행 중이었다면 그 작업을 계속한다).

## 범위 안 — 당연히 한다

| 구분 | 예 |
| --- | --- |
| 선언한 작업 자체 | 계획의 각 스텝 |
| 작업이 일으킨 사이드이펙트 수정 | 바꾼 함수의 호출부, 깨진 테스트, 타입 오류 |
| 작업 검증 | 테스트·빌드 실행, 설치돼 있는 검증 스킬(리팩터링 사이드이펙트 점검·화면 확인 등) |
| 작업 때문에 따라 바뀌어야 하는 문서 | 프로젝트 규칙·문서 가드가 요구하는 기능 문서·버전 기록 |
| 규칙이 정한 기록·보고 | 글로벌·프로젝트 `CLAUDE.md`가 작업 단위 종료 때 요구하는 기록, 커밋 전 확인·병합 안내 같은 보고 |

판단 기준: **이걸 안 하면 선언한 작업이 깨지거나 미완성인가?** 그렇다면 범위 안이다.

## 범위 밖 — 하지 않는다

- 관련돼 보이지만 작업 완료에 필요 없는 수정(옆 코드 정리, 리팩터링, 네이밍 개선)
- 다음 기능 착수, 다음 계획 스텝으로 넘어가기(선언이 "스텝 1~2"면 3은 범위 밖)
- 작업 중 발견한 별개의 버그 수정
- 구성·도구 추천 — 규칙이 "작업을 마친 뒤 추천하라"고 한 것도 따로 제안하지 않고 아래 목록에 한 줄로 넣는다

작업하며 읽거나 고친 코드에서 눈에 띈 것(별개의 버그·의심스러운 동작 등)은 고치지 않고 **완료 보고 끝에 `범위 밖 발견:` 목록으로 한 줄씩만** 적는다. 이 목록을 채우려고 작업과 무관한 코드를 따로 뒤지지는 않는다.
범위 안인지 애매하면 하지 말고 그 목록에 넣는다.

## 완료 시

1. 무엇을 했고 어떻게 검증했는지 보고한다.
2. `범위 밖 발견:`이 있으면 적는다.
3. 마지막 줄: `세션 범위 완료 — 이어서 하려면 /wrap 후 /clear → /resume`.
4. **멈춘다.** "다음으로 ~할까요?" 같은 후속 작업 제안이나 착수를 하지 않는다.

## 사용자가 범위 밖 작업을 직접 요청하면

사용자의 명시적 요청이 이 범위보다 우선한다. `범위 확장: <요청>` 한 줄을 적고 진행한다.
