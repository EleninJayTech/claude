# ops-kit

혼자 만든 프로젝트를 **배포하고 운영하는 사람(운영자 1명)** 이 개발하지 않는 시간에 보고 따라 할 문서·화면·안전장치를 만든다. 스택은 가리지 않는다(웹앱·봇·CLI·서버리스 Worker). 이 스킬이 만드는 것은 7종이고, 무엇이 필요한지는 프로젝트마다 다르다 — 그래서 **진단이 먼저고, 사용자가 고른 것만 만든다.**

| # | 산출물 | 참조 파일 |
| --- | --- | --- |
| ① | 배포 런북 — 첫 배포·재배포·롤백 | `references/runbook-deploy.md` |
| ② | 운영 런북 — 배포 뒤 사람이 할 일·정기 점검 | `references/runbook-ops.md` |
| ③ | 관리 허브 — 앱별 관리 사이트·계정 이름·확인 위치 | `references/hub.md` |
| ④ | 관리자 대시보드 — 앱 서버의 `/admin`·JSON API | `references/dashboard.md` |
| ⑤ | 헬스체크·장애 알림 | `references/health.md` |
| ⑥ | 백업·복구 리허설 | `references/backup.md` |
| ⑦ | 무료 한도·비용 감시 | `references/limits.md` |

①~④는 **기본 추천**(배포 대상이 있으면 대개 필요하다), ⑤~⑦은 **선택**이다. 둘 다 진단을 거친다 — 서버·DB가 없는 프로젝트에 대시보드를 얹으면 쓸모없는 코드만 늘어난다. HTML 산출물(①②③)의 골격은 `references/page-shell.md` 하나를 함께 쓴다.

## 0. 원칙

- **진단 없이 만들지 않는다.** 진단 표를 보이고 사용자가 고르기 전에는 파일을 하나도 만들지 않는다. 작은 프로젝트에 필요 없는 장치를 얹는 것이 이 스킬이 막으려는 실패다.
- **배포·시크릿 입력·외부 알림 채널 연결은 하지 않는다.** 그것은 사용자가 런북을 보고 직접 한다. 이 스킬은 그 런북을 만든다. 사용자가 명시적으로 시켜도 시크릿 값은 받지 않는다 — 값이 채팅 기록에 남는다.
- **시크릿 값·비밀번호·토큰은 문서에도 채팅에도 쓰지 않는다.** 이름과 보관 위치(예: "비밀번호 관리자의 `<항목명>`")만 쓴다.
- **유료 도구를 전제하지 않는다.** 모니터링 SaaS 없이 호스팅의 무료 기능·GitHub Actions 같은 무료 범위에서 해결한다.
- **외부 수치는 박지 않는다.** 한도·수수료·보관 기간·최소 간격은 작성하는 날 공식 문서(라이브러리·CLI는 `ctx7`이 있으면 그것)로 확인해 확인일을 붙이고, 확인하지 못한 값엔 `[재확인]`을 붙인다. 이 값들은 자주 바뀌고, 박아 둔 값은 조용히 틀린다.
- **`.env`·키 파일은 읽지 않는다.** 시크릿 이름은 설정 파일·타입 정의·`.env.example`에서 얻는다.

## 1. 모드

| 인수 | 하는 일 | 파일 쓰기 |
| --- | --- | --- |
| `init` | §2 조사 → §3 진단 표(7종) → 선택 → 고른 것만 생성 | 승인 후 |
| `runbook` · `hub` · `dashboard` | 기본 산출물 하나(`runbook`은 ①② 둘 — 어느 쪽인지 물어 하나만 해도 된다)를 진단 → 생성·갱신 | 승인 후 |
| `health` · `backup` · `limits` | 선택 산출물 하나를 진단 → 필요하면 생성 | 승인 후 |
| `sync` | 최근 커밋·배포 설정을 산출물과 대조해 뒤처진 것과 새 진단 신호를 보고 → 승인 후 수정 | 승인 후 |
| `check` | 읽기 전용 점검(§7) | **쓰지 않는다** |

인수가 없으면: 상태 파일(`docs/status/ops-kit.md`)이 없으면 `init`을, 있으면 `check`를 제안하고 고르게 한다.
`check`·`sync`를 불렀는데 상태 파일이 없으면 아무것도 만들지 않고 "먼저 `/ops-kit init`을 실행하라"고 안내하고 끝낸다.

**산출물 언어**: 대상 `CLAUDE.md` 맨 아래 드롭인 적용 기록에 산출물 언어가 적혀 있으면 그것을, 없으면 사용자와 대화하는 언어를 쓴다.

## 2. 조사

읽기만 한다. 찾은 것마다 **파일:줄 또는 설정 키**를 적어 둔다 — 진단 표의 근거 칸이 된다.

- **배포 명령**: `package.json` scripts(`deploy`·`release`), `Makefile`, `justfile`, CI 워크플로(`.github/workflows/*`의 배포 단계).
- **호스팅 설정**: `wrangler.toml`/`wrangler.jsonc`·`fly.toml`·`vercel.json`·`netlify.toml`·`render.yaml`·`Dockerfile`·`Procfile`·`app.yaml`·`serverless.yml`. 상시 실행인지(서버·Worker·봇) 정적 배포인지 가른다.
- **시크릿 이름**: 설정 파일의 바인딩·env 타입 정의·`.env.example`·런타임 코드의 `env.X`·`process.env.X`. 값은 보지 않는다.
- **DB·스토리지**: D1·SQLite 파일·Postgres·MySQL·KV·버킷 바인딩, 마이그레이션 폴더, ORM 스키마.
- **이벤트·사용자 데이터**: 사용자 테이블, 이벤트 테이블·로깅 호출(세션 시작·핵심 행동·결제).
- **외부 서비스**: 외부 API·LLM SDK 의존성, 결제(스토어·PG), 도메인, 봇 플랫폼, 메일.
- **알림 채널 후보**: 봇 토큰 이름·메일 발송·웹훅 URL 이름.
- **기존 운영 문서**: `docs/status/`·`docs/runbook*`·`RUNBOOK*`·`OPERATIONS*`·`DEPLOY*`. 있으면 내용을 훑어 무엇을 이미 다루는지 적는다.
- **상태 파일**: `docs/status/ops-kit.md`가 있으면 기각 기록·확인일을 읽는다.

## 3. 진단 표

각 산출물의 판정 기준은 그 참조 파일의 `## 진단 신호` 절에 있다. 7개 참조 파일의 그 절만 읽어 판정한다(나머지 절은 만들 항목을 고른 뒤 읽는다).

이 형식을 그대로 쓴다:

```markdown
| # | 산출물 | 판정 | 근거 | 만들 것 |
| --- | --- | --- | --- | --- |
| ① | 배포 런북 (기본 추천) | 필요 | `wrangler.toml:1` name · `package.json:6` deploy | 첫 배포·재배포·롤백 3절 |
| … | | | | |
| ⑤ | 헬스체크·장애 알림 (선택) | 불필요 | 상시 실행 없음 — 정적 배포(`.github/workflows/pages.yml:12`) | — |
```

- 판정은 `필요` / `불필요` / `판단 보류` 셋 중 하나다. **근거 없는 판정은 쓰지 않는다** — 근거가 없으면 `판단 보류`이고, 무엇을 확인하면 정해지는지 근거 칸에 적는다.
- ①~④를 위에 "(기본 추천)", ⑤~⑦을 아래에 "(선택)"으로 둔다.
- 상태 파일 기각 기록에 있는 항목은 `불필요(기록됨 YYYY-MM-DD)`로만 보이고 다시 권하지 않는다. **새 진단 신호가 그 이유를 뒤집을 때만**(예: "DB 없음"으로 기각했는데 DB가 생겼다) 근거와 함께 다시 묻는다.
- 이미 있는 운영 문서가 같은 역할을 하면 판정 옆에 `(기존: <경로>)`를 붙이고, 고를 때 **유지(상태 파일에 등록만) / 재구성(형식만 맞춤) / 교체** 를 묻는다. 말없이 덮지 않는다 — 사용자가 손으로 고친 내용이 있을 수 있다.

표를 보인 뒤 AskUserQuestion(multiSelect)으로 만들 항목을 받는다(선택지는 `필요`·`판단 보류`인 항목, 기본 추천을 앞에). 사용자가 표까지만 보자고 했거나 질문할 수 없는 환경이면 표를 보이고 멈춘다.
고르지 않은 `불필요` 항목은 생성 단계에서 상태 파일 기각 기록에 이유와 날짜로 남긴다 — 다음 진단이 같은 제안을 반복하지 않게.

## 4. 공통 작성 규칙 (①②③ 그리고 ⑤⑥⑦이 런북에 넣는 단계)

**단계 블록**: 런북의 모든 단계는 아래 네 칸을 갖는다. 운영자는 개발하지 않는 시간에 이 문서만 보고 따라 하므로, 한 칸이라도 비면 그 자리에서 막힌다.
1. **명령** — 붙여 넣으면 그대로 도는 블록. 실행 위치(폴더)를 첫 줄 주석으로 적는다. 자리표시자는 `<이름>`으로 쓰고 바로 아래에 무엇으로 바꾸는지 적는다.
2. **성공하면 보이는 문구** — 출력에서 찾을 문자열(예: `Success! Uploaded`·`{"ok":true`). 공식 문서나 실제 출력으로 확인한 문구만 쓰고, 아니면 `[재확인]`.
3. **실패하면** — 흔한 실패 1~3개와 대처. 모르는 실패는 "출력 첫 줄을 Claude에게 보낸다".
4. **Claude에게 보낼 보고** — 결과를 붙여 보내면 다음 세션이 이어받을 수 있는 한 줄 틀:
   `[ops-kit <문서 id>/<단계 id>] 결과: <성공 문구 또는 오류 첫 줄> · 다음: <단계 id>`

**시크릿 입력**: 클립보드·Ctrl+V로 넣게 하지 않는다. 붙여넣기가 조용히 실패해 짧은 값(실사례: 10자)이 들어가도 명령은 성공해 버린다. 대신 숨김 입력으로 변수에 받고, **길이를 먼저 출력해 확인**한 뒤 파이프로 넘긴다:

```powershell
# PowerShell 7
$t = Read-Host -MaskInput "NAME"; $t.Length
$t | npx wrangler secret put NAME
Remove-Variable t
```
```bash
# bash
read -rs -p "NAME: " t; echo; echo ${#t}
printf %s "$t" | npx wrangler secret put NAME
unset t
```

위는 형태 예시다. 실제 CLI가 표준 입력을 받는지·플래그는 작성하는 날 공식 문서로 확인한다(받지 않으면 그 CLI의 파일·환경변수 입력 방식을 쓰고, 그것도 길이 확인을 앞에 둔다). 기대 길이(예: "32자 이상")를 단계에 적어 둔다.

**외부 사실**: 확인하지 못한 수치(수수료·보관 기간·한도·최소 간격)엔 `[재확인]`을 붙인다. 외부 콘솔 메뉴 경로("Settings → …")는 공식 문서로 확인한 것만 쓰고 확인일을 붙인다 — 콘솔 UI는 예고 없이 바뀌어, 기억으로 쓴 경로는 운영자를 헤매게 한다. 확인 못 하면 "콘솔에서 `<찾을 것>`을 찾는다"로 쓴다.

**정기 항목**: `다음 ○○: YYYY-MM경` 형식으로 쓴다(예: `다음 백업 점검: 2027-02경`). 대상 repo에 `docs/PROJECT_PLAN.md`가 있으면 같은 줄을 거기에도 한 줄 올린다(승인 범위에 포함해 묻는다) — 세션 재개 절차는 PROJECT_PLAN의 예정일을 읽지만 HTML 런북 안은 보지 않는다.

**사실이 틀린 게 밝혀지면**: 런북에 적힌 것이 실제와 다르다는 것이 드러나면(재배포가 필요 없는데 필요하다고 적었다 등) 그 세션 안에 고쳐 다시 게시하고 상태 파일 확인일을 갱신한다. 틀린 런북은 없는 런북보다 위험하다 — 운영자는 의심하지 않고 따른다.

## 5. 게시

- 원본은 대상 repo의 `docs/status/<이름>.html`이다. 골격은 `references/page-shell.md`를 쓴다(다크 모드·모바일 폭·시스템 폰트 — 웹폰트를 쓰지 않아 폰트 라이선스 판단이 필요 없다).
- 하네스에 **Artifact 도구가 있으면** 그 도구의 규칙대로 **비공개**로 게시하고 URL을 상태 파일 `게시 URL` 칸에 적는다. 수정하면 **같은 URL로 재게시**한다(새 URL을 만들면 운영자가 북마크한 옛 페이지가 낡은 채 남는다). 사용자가 게시하지 말라고 했으면 하지 않는다.
- 도구가 없으면 로컬 경로만 알린다(브라우저로 열 수 있다).
- 프로젝트에서 `kr-ui-guide` 스킬을 쓸 수 있고 산출물 언어가 한국어면 그 기준(대비·터치 영역·마이크로카피)을 따른다.
- 새 앱을 배포했거나 설정이 바뀐 세션은 허브(③) 목록을 고쳐 다시 게시한다. 새 계정·관리 사이트 위치가 나오면 허브에 적는다(비밀번호류 제외).

## 6. 상태 파일 `docs/status/ops-kit.md`

진단 판정·기각 이유·게시 URL·확인일·예정일을 한곳에 둔다. `sync`·`check`와 다음 세션이 이것을 읽는다. 처음 무엇이든 만들 때 이 형식으로 만든다:

```markdown
# ops-kit 상태

| 산출물 | 판정 | 근거 | 파일 | 게시 URL | 확인일 |
| --- | --- | --- | --- | --- | --- |
| ① 배포 런북 | 필요 | `wrangler.toml:1` | docs/status/deploy-runbook.html | — | YYYY-MM-DD |

## 기각 기록 (다시 권하지 않는다)
- ⑤ 헬스체크 불필요 — 상시 실행 없음(정적 배포) (YYYY-MM-DD)

## 한도 표 확인일
- YYYY-MM-DD

## 예정
- 다음 백업 점검: YYYY-MM경
```

확인일은 그 산출물의 사실을 마지막으로 대조한 날이다. 내용을 고치지 않고 대조만 했어도 갱신한다.

## 7. sync · check

**sync** — 상태 파일의 가장 최근 확인일 이후 변경을 본다:
1. `git log --since=<확인일> --name-only`와 배포 설정 파일의 diff를 읽는다.
2. 산출물마다 대조한다: 런북 단계의 명령·폴더·스크립트 이름, 허브 링크·계정 이름, 대시보드 지표가 읽는 테이블·이벤트, 헬스체크 대상 경로, 백업 대상 DB·테이블, 한도 표의 서비스 목록.
3. §2 조사를 다시 돌려 **새 진단 신호**(DB·외부 API·상시 실행·결제가 새로 생김)를 찾는다. 기각 기록의 이유를 뒤집는 신호면 따로 표시한다.
4. `| 산출물 | 뒤처진 곳 | 근거(커밋·파일:줄) | 고칠 내용 |` 표로 보고하고 승인받은 것만 고친다. 고친 산출물은 재게시하고 확인일을 갱신한다.

**check** — 아무것도 쓰지 않는다(상태 파일 확인일도 갱신하지 않는다):
- **지난 예정일**: 상태 파일·런북의 `다음 ○○: YYYY-MM경`이 이번 달보다 앞이면 보고.
- **`[재확인]`**: 산출물 전체에서 개수와 위치(파일·문맥 한 줄).
- **오래된 확인일**: 한도 표 확인일이 90일을 넘었으면, 다른 산출물 확인일이 180일을 넘었으면 보고.
- **링크**: 산출물 안의 `http(s)` 링크를 HEAD 요청(실패하면 GET)으로 확인해 4xx·5xx·연결 실패를 보고한다. 로그인이 필요한 콘솔 링크의 401·403은 "로그인 필요 — 정상일 수 있음"으로 따로 둔다. 네트워크를 쓸 수 없으면 건너뛰었다고 적는다.
- **상태 파일과 실물 불일치**: 표에 있는데 파일이 없거나, `docs/status/`에 있는데 표에 없는 것.
결과는 `| 구분 | 위치 | 내용 | 권하는 조치 |` 표 하나로 내고, 고칠 것이 있으면 `/ops-kit sync`(또는 해당 모드)를 권한다.

## 8. 하지 말 것

- 묻지 않고 배포하거나, 시크릿을 넣거나, 외부 알림 채널(봇·메일·웹훅)을 연결하지 않는다.
- 모니터링 SaaS·유료 도구를 전제하지 않는다.
- 진단 없이 7종을 전부 만들지 않는다. 진단 표 승인 전에는 파일을 만들지 않는다.
- `.env`·키·인증서 파일을 읽지 않는다. 시크릿 값을 문서·채팅·커밋 메시지에 쓰지 않는다.
- 백업 파일·내보낸 데이터를 저장소에 커밋하지 않는다.
- 생성한 코드(대시보드·`/health`·점검 워크플로)를 사용자 확인 없이 커밋·푸시하지 않는다.
