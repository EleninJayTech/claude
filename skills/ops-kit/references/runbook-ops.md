# ② 운영 런북 — 배포 뒤 사람이 할 일 · 정기 점검

배포가 끝나도 운영자가 손으로 해야 하는 일이 남는다 — 외부 콘솔에서 무언가를 켜고, 행정 절차를 밟고, 주기적으로 무언가를 확인한다. 이것들은 코드에 흔적이 없어 잊히기 쉽다. 이 문서가 그 목록이다.

## 진단 신호

| 판정 | 조건 |
| --- | --- |
| 필요 | 외부 콘솔(호스팅·DB·스토어·결제·도메인·봇 플랫폼·분석) 중 하나라도 쓰거나, 결제·사업자·세무·약관 같은 행정 절차가 있거나, 정기로 확인할 것(백업·한도·인증서·도메인 만료)이 있다 |
| 불필요 | 배포 대상이 없거나, 배포 후 사람이 할 일이 전혀 없다(근거를 적는다 — 드물다) |
| 판단 보류 | 외부 서비스는 보이는데 운영자가 손으로 하는 일이 있는지 코드로 알 수 없다 → 사용자에게 물을 질문을 근거 칸에 적는다 |

## 만들 것

`docs/status/ops-runbook.html`(문서 id `ops`). 절 순서:

1. **배포 직후 할 일** — 한 번만 하는 일(콘솔에서 기능 켜기·웹훅 확인·결제 테스트·스토어 정보 입력). 각각 단계 블록.
2. **외부 콘솔 목록** — 표 `| 콘솔 | 여기서 확인하는 것 | 위치(메뉴 경로 — 공식 문서로 확인한 것만, 확인일) | 계정 이름 |`. 계정은 **이름만**(로그인 ID가 이메일이면 그대로 둘지 사용자에게 묻는다).
3. **행정 절차** — 사업자·세무·약관·개인정보 처리방침·스토어 정책처럼 코드 밖의 일. 기한·수수료·보관 기간 같은 외부 수치엔 확인일 또는 `[재확인]`. 이 영역은 사실 확인이 특히 어려우므로 **모르는 것은 모른다고 쓰고** 확인할 곳(공식 기관·플랫폼 도움말)을 적는다.
4. **정기 점검** — 항목마다 주기와 `다음 ○○: YYYY-MM경` 한 줄. 예: 한도 확인(⑦)·백업 리허설(⑥)·인증서·도메인 만료·의존성 보안 업데이트. 대상 repo에 `docs/PROJECT_PLAN.md`가 있으면 같은 줄을 거기에도 올린다(SKILL.md §4).
5. **⑤⑥⑦ 운영 단계** — 만든 선택 산출물이 있으면 그 사람 몫 단계: 헬스체크 알림 채널 연결(토큰은 §4 시크릿 형식)·백업 리허설 절차·한도 확인 절차. 해당 참조 파일의 "런북에 넣을 단계"를 옮긴다.
6. **장애가 났을 때** — 첫 5분에 볼 것(헬스 엔드포인트·호스팅 상태 페이지·로그 명령)과 배포 런북 롤백 절 링크.

## 형식·템플릿

- 단계 id는 `ops/<절 번호>-<순번>`.
- 정기 점검 표: `| 항목 | 주기 | 다음 | 방법(단계 링크) |`, `다음` 칸은 `다음 ○○: YYYY-MM경` 문자열을 그대로 쓴다(검색되도록).
- 체크 표시(완료 여부)는 문서에 상태로 저장하지 않는다 — 완료는 운영자가 "Claude에게" 보고 틀로 알리고, 다음 세션이 런북의 예정일을 옮겨 적는다(브라우저 저장소에 둔 완료 표시는 기기마다 달라 사실이 갈린다).

## 검증

- 외부 콘솔 표의 메뉴 경로마다 확인일 또는 `[재확인]`이 있는지 본다.
- 정기 점검마다 `다음 ` + `YYYY-MM경` 형식 문자열이 있는지 정규식 `다음 .+: \d{4}-\d{2}경`으로 본다.
- 계정 칸에 비밀번호·토큰처럼 보이는 값이 없는지 본다.
- 상태 파일 표에 ② 행, `## 예정`에 정기 점검 줄을 추가·갱신한다.
