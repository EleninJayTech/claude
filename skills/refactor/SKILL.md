# refactor

원칙 하나로 요약하면: **동작은 그대로, 코드만 좋아진다. 그걸 증명할 수 없으면 하지 않는다.**

## 인수 해석

| 인수 | 범위 | 동작 |
|---|---|---|
| (없음) | 최근 개발분 | 리팩터링 → 사이드 이펙트 검증 |
| `all` | 프로젝트 전체 | 후보 인벤토리 → 승인 → 배치별 리팩터링·검증 |
| `경로` 또는 `커밋..커밋` | 지정 구간 | 리팩터링 → 검증 |
| `check [범위]` | 지정 범위(기본: 현재 diff) | **검증만** 수행. 새 세션에서 독립 검증할 때 씀 |
| 끝에 `nocheck` | — | 리팩터링만 하고 검증은 생략. 나중에 `/refactor check` 로 따로 |

"최근 개발분" 은 다음 순서로 정한다: 커밋되지 않은 변경 → 현재 브랜치가 기본 브랜치
(`git merge-base HEAD main|master|develop`)에서 갈라진 뒤의 커밋 → 그것도 없으면 최근 5커밋.
결정한 범위를 파일 목록과 함께 사용자에게 보여주고 시작한다.

## 절차

### 0. 준비
- 작업 트리가 더러우면(커밋 안 된 변경) 그 사실을 알린다. 리팩터링 전 상태로 돌아올 수 있게
  사용자에게 커밋 또는 스태시를 권하고, 거부하면 진행하되 되돌릴 방법을 보고에 남긴다.
- 언어·프레임워크·버전을 빌드 파일에서 읽는다 (package.json engines, pom.xml/build.gradle 의
  java 버전, pyproject, go.mod, Cargo.toml 등). 린터·포매터·테스트 명령도 찾는다.
- **기준선**: 기존 테스트를 먼저 돌려 통과/실패 목록을 기록한다. 이미 실패하던 것은
  리팩터링 탓이 아니므로 구분해 둔다. 테스트가 없으면 그 사실을 기록하고 4단계에서 보완한다.
- `docs/features/` 가 있으면 범위에 걸친 기능 문서(F-xxx)를 확인해 둔다. 검증 단계에서 쓴다.

### 1. 후보 찾기
`${CLAUDE_SKILL_DIR}/references/catalog.md` 의 네 범주로 범위를 훑는다.
후보마다 **무엇을 / 왜 / 위험도(낮음·중간·높음) / 영향 범위(호출처 수)** 를 적는다.

- 위험도 높음: 공개 시그니처·반환 타입·예외·순서 변경, 외부 I/O 경로, 동시성, 직렬화 형식
- 위험도 중간: 내부 함수 통합, 모듈 이동, 조건문 재구성
- 위험도 낮음: 이름 변경(내부), 데드 코드 제거, 포매팅, 중복 상수 추출

### 2. 승인
후보 표를 보여주고 **어느 것을 할지 사용자가 고르게 한다.** 승인 전에는 코드를 고치지 않는다.
`all` 모드에서는 후보가 많으므로 위험도 낮음→높음 순으로 배치를 나누어 제안한다.
하나의 배치는 검증 한 번으로 감당할 수 있는 크기(대략 파일 5개, 후보 10개 이내)로 한다.

### 3. 리팩터링
- 후보 하나 = 변경 하나. 섞지 않는다. 승인된 후보만 한다.
- 리팩터링과 기능 변경·버그 수정을 한 변경에 섞지 않는다. 진행 중 버그를 발견하면
  고치지 말고 보고에 "발견한 버그" 로 남긴다.
- 함수 통합 시: 통합 전 두 함수의 차이(인자 기본값, 예외, 반환값, null 처리, 부수효과)를
  표로 정리하고, 차이가 하나라도 있으면 그 차이를 보존하는 방식으로만 합친다.
  보존할 수 없으면 통합하지 않는다.
- 호출처는 문자열·리플렉션·템플릿·설정 파일·DI 등록·테스트까지 전부 찾는다
  (`references/side-effects.md` 의 검색 목록). IDE 없이 grep 만으로 찾으므로 이름이 짧으면
  단어 경계로 검색한다.
- 언어 버전 대응은 현재 버전에서 실제로 deprecated/removed 된 것만 바꾼다. "더 최신 문법"
  으로의 취향 변경은 후보에 올리되 위험도 낮음·선택으로 표시한다.
- 성능 개선은 측정 근거(프로파일, 복잡도, 호출 빈도)가 있는 것만 한다. 추정으로 하지 않는다.
- 각 변경 후 린터·포매터·컴파일(타입체크)을 바로 돌린다.

### 4. 사이드 이펙트 검증
`${CLAUDE_SKILL_DIR}/references/side-effects.md` 의 체크리스트를 전부 수행한다. 요약:
1. 기준선 테스트 재실행 → 새로 실패한 것만 문제로 본다.
2. 변경된 함수의 모든 호출처를 다시 열어 계약(인자·반환·예외·순서)이 유지되는지 읽는다.
3. 테스트가 없던 영역은 리팩터링 전후 출력을 비교하는 특성화 테스트(characterization test)를
   추가한다. 최소한 대표 입력 3개(정상·경계·오류)로 전후 결과가 같은지 확인한다.
4. `docs/features/` 가 있으면 영향 기능의 TC 를 `/feature-test F-xxx` 로 실행한다.
   화면·API 동작이 바뀌지 않았어야 한다.
5. 정적 확인: 타입체크, 린트, 빌드, 의존성 순환.
6. 런타임 확인이 필요한 항목(DB 쿼리 결과, 외부 API 호출 형식, 로그 포맷, 스케줄러)은
   실제로 실행해 보거나, 못 하면 "미검증" 으로 명시한다.

`check` 모드는 이 단계만 수행한다. 범위는 인수 또는 현재 diff 다.

### 5. 보고
`${CLAUDE_SKILL_DIR}/references/report.md` 형식으로 채팅에 출력한다. 요청이 있으면
`docs/refactor/YYYY-MM-DD_<범위>.md` 로 저장한다. 커밋은 하지 않는다 — 사용자가 한다.
변경 하나가 커밋 하나가 되도록 권한다.

## 하지 않는 것
- 승인 없는 코드 변경, 기능 변경, 버그 수정, 공개 API 변경, 의존성 추가·업그레이드
- 테스트를 통과시키기 위한 테스트 수정 (테스트가 틀렸다고 판단되면 보고만)
- "미검증" 을 "통과" 로 쓰는 것
