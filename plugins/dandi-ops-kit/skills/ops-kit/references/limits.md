# ⑦ 무료 한도 · 비용 감시

무료 플랜으로 운영하는 프로젝트에서 가장 흔한 사고는 장애가 아니라 **한도 초과**다 — 조용히 요청이 막히거나, 조용히 과금이 시작된다. 둘 다 운영자는 늦게 안다. 이 산출물은 "무엇이 어디서 막히고 어디서 확인하는가"를 한 표로 만든다.

## 진단 신호

| 판정 | 조건 |
| --- | --- |
| 필요 | 무료 플랜·무료 크레딧으로 쓰는 서비스가 하나라도 있다(호스팅·DB·스토리지·외부 API·LLM·메일·도메인 외) |
| 불필요 | 외부 서비스가 없다(로컬 전용) |
| 판단 보류 | 쓰는 서비스는 보이는데 어느 플랜인지 코드로 알 수 없다 → 사용자에게 플랜을 묻는다 |

## 만들 것

1. **한도 표** — 운영 런북(②)에 절로 넣는다:

   ```markdown
   | 서비스 | 한도 | 단위 | 넘으면 | 확인 위치 | 확인일 |
   | --- | --- | --- | --- | --- | --- |
   | <호스팅> | <수치> | 요청/일 | 요청 거부(무료) / 과금 시작(유료 전환 시) | <콘솔 메뉴 또는 API> | YYYY-MM-DD |
   | <LLM API> | [재확인] | 토큰/월 | | | — |
   ```

   - **수치는 그날 공식 요금·한도 페이지에서 확인한 값만** 쓰고 확인일을 적는다. 확인하지 못했으면 수치 칸에 `[재확인]`, 확인일 칸에 `—`. 기억이나 블로그 글의 수치는 쓰지 않는다 — 한도는 예고 없이 바뀐다.
   - `넘으면`은 "막힌다"와 "돈이 나간다"를 구분해 쓴다 — 대응이 정반대다(앞은 기능 저하, 뒤는 결제 수단 확인·상한 설정).
   - 결제 수단이 연결된 서비스면 **지출 상한·예산 알림 기능이 있는지**를 공식 문서로 확인해 표 아래에 적는다(있으면 켜는 단계를 운영 런북에 — 켜는 것은 사용자가 한다).
2. **사용량 읽기 가능 여부** — 서비스마다 사용량을 API로 읽을 수 있는지(공식 API·CLI) 확인한다.
   - **읽을 수 있고 ④ 대시보드가 있으면**: 대시보드에 "한도 대비 사용량" 칸을 넣는다 — 사용량 / 한도, **80% 이상이면 경고색**. 읽기 API 토큰은 읽기 전용 권한으로, 시크릿에 둔다. API 호출은 대시보드 요청마다가 아니라 짧은 캐시(예: 10분)를 둔다.
   - **읽을 수 없으면**: 운영 런북 정기 점검에 "콘솔에서 사용량 확인" 단계를 넣는다(확인 위치·`다음 한도 점검: YYYY-MM경`, 기본 월 1회).
3. 상태 파일 `## 한도 표 확인일`과 허브 `ops.limitsCheckedAt`을 갱신한다.

## 형식·템플릿

80% 경고 계산(대시보드 쪽, 스택 무관):

```ts
type Usage = { service: string; used: number; limit: number; unit: string; checkedAt: string };
const ratio = (u: Usage) => (u.limit > 0 ? u.used / u.limit : null);
const level = (r: number | null) => (r === null ? "unknown" : r >= 1 ? "over" : r >= 0.8 ? "warn" : "ok");
```

한도 수치(`limit`)는 코드에 상수로 박지 않고 설정·시크릿이 아닌 일반 변수(예: `[vars]`)로 둔다 — 한도가 바뀌면 재배포 없이 바꿀 수 있고, 확인일과 함께 갱신하는 자리가 한 곳이 된다.

## 검증

- 한도 표의 모든 수치 칸이 확인일을 갖거나 `[재확인]`인지 본다(둘 다 없는 칸은 0개여야 한다).
- 확인일이 90일을 넘은 행이 있으면 `check` 모드가 보고한다 — 이 산출물을 갱신할 때 그런 행을 다시 확인한다.
- 대시보드에 칸을 넣었으면 80%·100% 경계값 테스트(0.79→ok, 0.8→warn, 1.0→over, limit 0→unknown).
- 상태 파일 표에 ⑦ 행을 추가·갱신한다.
