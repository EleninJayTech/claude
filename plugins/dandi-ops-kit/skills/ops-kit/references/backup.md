# ⑥ 백업 · 복구 리허설

백업은 **복원해 본 적이 있어야** 백업이다. 내보내기 명령만 있고 복원을 한 번도 안 해 봤으면, 정작 필요한 날 파일이 비었거나 형식이 안 맞는다는 것을 그때 안다. 그래서 산출물의 중심은 복구 리허설이다.

## 진단 신호

| 판정 | 조건 |
| --- | --- |
| 필요 | 영속 DB·스토리지(D1·SQLite 파일·Postgres·MySQL·KV·오브젝트 버킷)에 사용자 데이터·결제 기록처럼 다시 만들 수 없는 것이 쌓인다 |
| 필요(리허설만) | 호스팅이 자동 백업·시점 복구를 제공한다 — 보관 기간과 복원 방법을 **공식 문서로 확인해** 표에 적고, 그 복원 경로를 리허설한다 |
| 불필요 | 영속 데이터가 없거나, 전부 다시 만들 수 있다(캐시·빌드 산출물·외부에서 다시 받는 데이터) — 근거를 적는다 |
| 판단 보류 | 저장소는 있는데 무엇이 쌓이는지 코드로 알 수 없다 |

## 만들 것

운영 런북(②)에 **백업** 절을 넣는다(별도 HTML을 만들지 않는다 — 운영자가 볼 곳을 늘리지 않는다). 내용:

1. **현황 표**: `| 저장소 | 종류 | 담긴 것 | 개인정보 | 호스팅 자동 백업·보관 기간(확인일) | 복원 방법 |`.
2. **내보내기 단계** — 저장소마다. 명령 후보(플래그는 작성하는 날 공식 문서·`--help`로 확인):
   - D1: `wrangler d1 export <DB> --remote --output <파일>`
   - SQLite: `sqlite3 <db 파일> ".backup '<파일>'"`(실행 중 앱이 쓰는 파일이면 일관성 확인)
   - Postgres: `pg_dump --format=custom --file <파일> <연결>`(연결 문자열은 환경변수로 — 명령에 쓰지 않는다)
   - MySQL: `mysqldump`
   - KV·버킷: 공급자 CLI의 목록·내려받기, 또는 `rclone`
3. **보관 위치** — **저장소 밖**(개인 클라우드 드라이브·외장 디스크 등 사용자가 정한 곳). 파일명에 날짜(`<db>-YYYYMMDD.<ext>`). 보관 개수(예: 최근 4개).
4. **복구 리허설** — 운영 DB를 건드리지 않는다:
   1. 임시 DB를 만든다(로컬 SQLite·로컬 Postgres·호스팅의 임시 DB — 이름에 `rehearsal`).
   2. 백업 파일을 복원한다.
   3. 테이블별 행 수를 운영 쪽(읽기 전용 쿼리)과 대조한다: `| 테이블 | 운영 | 복원본 | 차이 |`. 백업 시각 이후 쌓인 만큼의 차이는 정상이다.
   4. 임시 DB를 삭제한다.
   5. 결과를 "Claude에게" 보고 틀로 남긴다 → 상태 파일·허브의 "마지막 백업 리허설" 날짜가 그것으로 갱신된다.
5. **정기**: `다음 백업 점검: YYYY-MM경`(기본 분기 1회 — 데이터가 빨리 쌓이면 더 자주). 운영 런북 정기 점검 표와 상태 파일 `## 예정`, 대상에 `docs/PROJECT_PLAN.md`가 있으면 거기에도.

## 형식·템플릿

행 수 대조 쿼리 예(SQLite 계열 — 테이블 목록은 `sqlite_master`에서):

```sql
SELECT name FROM sqlite_master WHERE type='table' AND name NOT LIKE 'sqlite_%' AND name NOT LIKE '_cf_%' ORDER BY name;
-- 테이블마다
SELECT '<table>' AS t, COUNT(*) AS n FROM <table>;
```

Postgres는 `SELECT relname, n_live_tup FROM pg_stat_user_tables`가 추정치이므로 리허설에서는 테이블마다 `COUNT(*)`를 쓴다.

## 검증

- 백업 파일에 개인정보(이메일·전화·결제 ID·사용자 ID)가 들어 있으면 **`.gitignore`에 백업 파일 패턴**(예: `*.sql`·`backups/`·`*-dump.*`)이 있는지 본다. 없으면 추가를 제안한다(승인 후). `git check-ignore -v <예시 파일명>`으로 확인한다.
- 내보내기 명령의 출력 경로가 저장소 안이 아닌지 본다.
- 리허설 단계가 운영 DB에 쓰는 명령(복원·삭제)을 갖지 않는지 본다 — 복원·삭제 대상 이름에 `rehearsal`이 들어 있어야 한다.
- 상태 파일 표에 ⑥ 행, `## 예정`에 `다음 백업 점검` 줄을 추가·갱신한다.
