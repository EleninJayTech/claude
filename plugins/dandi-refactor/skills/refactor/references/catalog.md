# 리팩터링 후보 범주

각 범주에서 찾을 것과 찾지 말아야 할 것. 후보로 올릴 때는 "무엇을 / 왜 / 위험도 / 호출처 수".

## 1. 중복 제거
찾는다:
- 이름은 다르지만 몸체가 거의 같은 함수·메서드 (인자 이름, 상수, 한두 줄만 다름)
- 같은 검증·변환·포매팅 로직이 여러 곳에 복사됨
- 같은 매직 넘버·문자열이 3곳 이상
- 비슷한 클래스가 공통 부모나 인터페이스 없이 나란히 존재

올리지 않는다:
- 두 번만 나오는 중복 (세 번째가 나올 때 합친다)
- 우연히 같아 보이지만 도메인이 다른 것 (주소 검증과 이메일 검증이 정규식 형태만 비슷한 경우)
- 합치면 조건 분기가 3개 이상 생기는 것 — 중복보다 나쁘다

통합 전 반드시 차이표를 만든다: 인자·기본값 / 반환값 / 예외 / null·빈값 처리 / 부수효과(로그, DB, 이벤트) / 호출 순서 의존.

## 2. 구조 정리
찾는다:
- 한 파일이 책임 셋 이상을 가짐 (컨트롤러 + 비즈니스 + 쿼리)
- 함수가 화면 하나를 넘김 (대략 60줄+) 이고 안에서 단계가 주석으로 구분됨 → 추출
- 매개변수 6개 이상 → 객체로 묶기
- 어디서도 호출하지 않는 함수·import·파일 (호출처 검색으로 확인, 진입점·리플렉션 제외)
- 이름이 하는 일과 다름 (`getUser` 가 저장도 함)
- 순환 의존
- 프로젝트 안에서 같은 일을 두 방식으로 함 (날짜 처리 라이브러리 두 개 등) → 하나로

올리지 않는다:
- 이미 팀 컨벤션인 구조 (CLAUDE.md, README, 기존 코드 다수가 따르는 방식)
- 파일 이동 자체가 목적인 변경 — 이동은 다른 후보의 부산물일 때만

## 3. 언어·런타임 버전 대응
- 빌드 파일의 목표 버전을 확인한 뒤, 그 버전에서 **실제로** deprecated / removed 된 API·문법만 후보로.
  확신이 없으면 공식 릴리스 노트를 검색해 근거 링크를 남긴다.
- 컴파일러·린터 경고 목록을 먼저 뽑는다 (`-Xlint`, `--strict`, `DeprecationWarning` 등).
- 프레임워크 메이저 업 후 남은 호환 shim, 폴리필, `// TODO: remove after upgrade`.
- 새 문법으로의 단순 치환(예: 람다, switch expression, f-string, optional chaining)은
  "취향" 으로 분류해 위험도 낮음·선택으로 표시. 사용자가 원할 때만.

## 4. 성능
근거가 있는 것만:
- 루프 안의 DB 조회·HTTP 호출 (N+1) — 호출 횟수를 세어 근거로
- 같은 값을 반복 계산 (루프 안에서 정규식 컴파일, 길이 계산, 설정 파싱)
- 큰 컬렉션을 통째로 메모리에 올린 뒤 일부만 사용
- 동기 I/O 가 요청 경로를 막음 (프레임워크가 비동기를 지원하는 경우)
- 문자열 누적 결합, 불필요한 복사, 잘못된 자료구조 (리스트에서 `contains` 반복)
- 인덱스 없는 컬럼으로 조회하는 쿼리 (스키마·마이그레이션 파일로 확인)

올리지 않는다:
- 마이크로 최적화 (측정 없이 "이게 더 빠를 것")
- 캐시 추가 — 무효화 정책이 필요하므로 리팩터링이 아니라 설계 변경. 후보에 "제안" 으로만.
